# 新需求会话开场模板

供治理会话在用户明确要求创建新需求会话时使用。根据实际资料填写，未确认的信息写明未知；不要把占位符当成真实需求内容发送。

## 创建前准备

- 使用项目列表工具确认 GreeSalesCloud 项目身份。
- 用户已明确要求直接使用保存的本地项目目录，创建会话时选 `environment: { type: "local" }`。任何时候都不创建 worktree，除非用户另外明确要求。
- 有需求编号就使用对应目录；标题和材料尚未提供时标为待提供。不要沿用上一需求的业务规则。
- 把本次授权阶段写入开场。未指定阶段时先读取上下文、确认材料和范围，不自动执行测试或录入知识库。
- 创建成功后，将实际需求会话的链接或 ID 记录到对应需求 README，方便治理会话后续定位审计对象。

## 开场正文

你负责本项目的需求 <编号>：<已知标题或“标题待提供”>。本会话专门处理该需求，项目治理会话负责跨需求流程审计和框架维护。

先阅读根目录 AGENTS.md、README.md，以及 requirements/<编号>/README.md；按实际工作需要阅读 context 中的环境、工具和用例规范。当前流程处于试行阶段，遵循现行规范并记录实际问题。

直接在当前本地项目目录工作，除非用户明确要求，否则不创建 worktree。完成有意义的工作单元或阶段更新后，检查本次文件并及时提交、push 到 origin/main；保留共享目录内其他会话或用户未完成的修改。

已确认信息：<需求编号、涉及系统、材料路径或链接、版本、此前已确认结论；只填写有依据的信息>。

本次工作范围：<用户明确要求的阶段与产物>。尚缺的信息：<关键缺口>。材料不足时提出聚焦问题，不编造规则；执行阶段所需账号和数据可在执行前补齐。

正式用例以思维导图展现，需要时使用 asynctest-mind；业务知识按指定项目通过 asynctest-kb 检索，写入按用户授权和工具确认流程进行。历史用例是结构参考，不是本期规则的默认依据。

阶段结束时更新需求入口的状态、结论、产物和下一步。在分析阶段结束、用例评审完成、测试收尾时提醒简短复盘，将有效做法和实际问题连同证据写入“流程复盘”，供治理会话审计。未查看或未执行的部分如实注明，不把试行建议描述为已验证成果。
