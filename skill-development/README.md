## 已确认的方向

依据用户本会话的明确要求：

1. 按标准 Skill 形式产出，并核对公司 SkillHub 的上传兼容性。
2. 引导是核心能力：表达自然、容易理解，帮助用户逐步开展测试。
3. 兼容用户的多会话工作方式，交接不能只依赖聊天历史。
4. 同时设计 Skill 自身目录和它引导用户建立的测试工作目录。
5. 考虑共享函数、配套 Skill、MCP 及不同测试环节，再逐环节设计。
6. 将设计与后续实现集中在本目录，区分“已确认／提议／待讨论”。

以上不代表具体目录字段、入口话术或各环节细节已获确认，也不代表已授权运行测试、写知识库或上传平台。

## 当前工作与下一步

已完成：建立设计入口、整体方案和首次使用草案。根据用户补充的多项目使用场景，增加被测项目层与状态归属设计；原“工作目录 → 需求”结构调整为“工作空间 → 被测项目 → 需求”。

下一步：先讨论项目身份、需求状态和跨会话恢复的边界，再补全首次使用引导。具体字段与实现均未定稿。

后续路线为提议：

| 顺序 | 工作 | 完成依据 |
| --- | --- | --- |
| 0 | 多项目归属与状态恢复 | 多个项目中的同号需求不串用，跨项目需求有唯一牵头记录，会话分别恢复自己的任务 |
| 1 | 首次使用与接入项目 | 初次启动、已有资料、跨会话续接的示例能清楚说明如何推进 |
| 2 | 逐环节设计 | 每个环节明确入口、输入、动作、产物、完成依据、衔接 |
| 3 | Skill 与必要工具实现 | 已确认设计有对应指令、模板或可运行实现 |
| 4 | 使用验证 | 真实的模拟任务覆盖首次使用、工具缺失、中断恢复等情况 |
| 5 | 打包与平台核验 | 标准校验、包内文件和平台解析结果逐项核对；上传需另行授权 |

## 目录维护约定

- 当前只创建有实际内容的设计文件。`skills/`、`tests/`、`dist/` 等在需要时创建。
- 讨论结论更新设计文档；实际实现推进时再更新 `skills/qa-workflow/`。
- 新建议先标为提议，不将助手建议自动升级为用户确认。
- 每次更新说明文件位置和变化；仅提交、推送本次核对过的内容。
- 不把现有业务材料、测试账号、截图、浏览器会话或平台身份信息复制进通用 Skill 包。
- 本目录当前位于内部测试仓库；以后单独开源时须明确发布文件范围、依赖和许可证。

项目现行工作依据为 [需求流程](../context/workflow.md) 和 [治理约定](../governance/README.md)。这些链接是内部设计来源，不应成为发布包必须依赖的外部文件。
