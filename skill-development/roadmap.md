# 测试工作流 Skill 推进计划

更新时间：2026-10-31。

本文件是 Skill 开发进度和下一步工作的统一入口。详细方案留在 design/，避免多份文档各自维护一套推进顺序。

## 当前所在位置

- 当前：第 1 步，基础模型设计中；1.1 身份与归属的概念设计已确认。
- 下一项：1.2，共享与差异；讨论复用内容、适用项目、版本和项目例外。
- 已有：整体设计、首次使用、多项目隔离、共享内容四份讨论稿。
- 尚无：可运行的 Skill、正式配置结构、状态管理实现、工具适配实现和验证结论。
- 公司平台只完成上传页要求的只读检查；标准包上传、安装和宿主行为尚未验证。

本次推进计划不代表已授权实施全部阶段、执行真实业务测试或发布。继续按用户指定的当前环节推进，已明确的结论和既有授权无需反复询问。

## 已确定的方向

来自用户明确需求：标准 Skill 形式、人性化引导、多会话接续、一个 Agent 工作空间中的多被测项目、项目间共用内容、持久化任务进度、良好的包与工作目录、逐环节设计、后续开源和公司平台使用。

当前候选结构、字段、话术、共享版本机制、工具组合及实际兼容范围仍需设计或验证。文件存在表示已形成草案，不表示能力已经实现。

## 第 1 步：基础模型的具体顺序

| 子项 | 要定下来的内容 | 使用的草案或待补内容 | 状态 |

| 1.2 共享与差异 | 哪些内容复用、适用哪些项目、引用哪一版、项目例外怎么保存、共用内容更新如何处理 | [共享内容与项目差异](design/shared-resources.md) | 下一项；已有草案 |
| 1.3 状态与恢复 | 各阶段状态、材料和产物版本、待办、阻塞、未知操作结果、何时保存；摘要与结构化数据如何保持一致 | 后续在设计需要时补状态契约，不先创建空 schema | 待设计 |
| 1.4 多会话协作 | 每个会话负责的任务、状态写入责任、共享页面和导图占用、交接与更新冲突如何处理 | 现有项目归属草案提供边界，具体机制待补 | 待细化 |

1.1 已用 71652 跨客户端与管理端、两个项目中的同号需求（虚构编号 12345）、71417 跨项目单点登录说明身份与归属。用户于 2026-10-31 同意商用订单作为一个被测项目、客户端与管理端作为两个系统。

后续继续用这些例子说明共享引用、状态变化和会话交接，再固定最小配置与目录结构。概念讨论不代替实际能力验证。

本步不预先搭建真实项目目录、不迁移历史需求，也不把项目隔离设计当成宿主安全权限的实现。

## 第 2 步：引导体验的核对顺序

以 [首次使用草案](design/onboarding.md) 为基础，依次讨论：

1. 新用户只有“想开始测试”的意图。
2. 用户已经给出需求、原型或用例。
3. 接入一个已有测试项目。
4. 在同一工作空间新增另一个被测项目，复用已确认内容。
5. 新会话继续旧任务，或同一会话切换任务。
6. 缺少材料、工具不可用、来源冲突或操作结果不明。

每种情况都展示用户实际会看到的话术、Agent 接下来会做的事及保存内容。已知信息不重复询问；必要问题解释用途；当前可独立完成的工作继续推进。引导表现不以固定话术匹配判断。

## 第 3 步：逐个设计测试环节

| 顺序 | 环节 | 重点与拟交付 |
| --- | --- | --- |
| 3.1 | 需求接收与分析 | 原始材料、既有知识、已确认规则、推断和待确认项；范围、风险与可核对的验收条件 |
| 3.2 | 页面取证 | 全范围核对、定向采样、已有能力复用、页面未部署的处理；明确取证与正式测试的区别 |
| 3.3 | 用例编写 | 按独立场景组织，准备／连续编号动作／对应预期；普通和跨角色示例、真实页面动作、命名与版本 |
| 3.4 | 用例评审 | 需求覆盖、重复与遗漏、可执行性、调整记录；区分已生成、待评审和已评审 |
| 3.5 | 测试执行 | UI 与接口测试分别明确适用范围、环境、角色、数据、预期和证据；执行标记、进度、阻塞、数据恢复 |
| 3.6 | BUG 记录与提交 | 失败场景与 BUG 关联、归因依据、简洁正文、账号引用与指定正文处理、截图位置；提交授权、去重、图片关联与回读 |
| 3.7 | 修复验证 | 人工触发或明确授权的复测、复现原问题、关联回归、结果更新；复测通过与关闭工单分别处理 |
| 3.8 | 知识沉淀 | 本期确认规则、差异、来源、版本、主条目与引用；写入及回读结果，避免复制全部用例 |
| 3.9 | 收尾与复盘 | 正式用例、知识内容、指定产物、未完成项和接手入口；基于证据改进流程 |

知识沉淀、规则澄清和用例修订可以在多个环节发生；表格是设计顺序，不要求每次任务从第一项开始，更不构成整条流程自动执行授权。

每个环节固定回答六件事：入口、输入、Agent 动作、产物、完成依据、衔接与恢复。以少量具体示例评审，确认后再进入下一个环节。

## 第 4—5 步：工具与实现范围

优先审查现有经验：思维导图、知识库、Chrome DevTools 与无界面执行、截图标注、禅道 API 提交及图片验证、查询查看通用件。可选的测试计划表同步按需要设计，不成为所有用户必配项。

实际清单逐项记录来源、版本、适用环境、所需权限、输入输出、写入副作用、错误和未知结果处理、验证范围。查明旧能力是可运行实现还是操作说明，移植时保留这一区别；同一功能不重复复制实现。

首版建议先复现一套已验证的工具组合并明确支持范围。接口执行方式、其他导图／缺陷平台、不同宿主的能力逐项决定；格式符合标准不等于在所有宿主和工具上已跑通。

实现按以下次序分批推进：

1. 标准入口、项目定位、按需加载与最小工作目录。
2. 状态保存、读取恢复、共享引用和基本冲突处理。
3. 已设计的阶段指令、产物模板及必要的稳定脚本。
4. 已确定的外部工具适配和端到端连接。

实现只依据已确认设计，不用占位函数、空目录或承诺代替功能。是否进入实现按届时用户指令推进。

## 第 6—8 步：验证、试用与发布

验证至少覆盖：首次使用、已有项目接入、同号需求、多项目共享与差异、跨项目需求、多会话交接、共享资源冲突、断线后的未知写入结果、缺少工具、规则更新影响、失败用例与 BUG 数量关系、附件可见性及一次完整需求闭环。

先用虚构资料和可控环境验证；真实业务操作、上传或公开发布按各自授权推进。未获授权不启动子代理、新会话或实际业务测试。

性能对照使用相同任务、材料和工具条件，记录工具调用数、返回文本量、耗时及实际可获得的 token 指标。字符或分词估算标为估算，不将格式校验或局部速度提升当成整体效果结论。

公司平台核对 ZIP 目录层级、标准元数据、附属文件、依赖及更新行为。Codex、WorkBuddy 等宿主分别列为已验证／部分验证／未验证，不能相互替代证据。实际无法访问的宿主保留未验证项。

开源发布只包含明确选择的通用源码、示例、文档和验证资料；具体名称、许可证与分发方式在发布准备时确定。升级演练需验证团队共享内容、项目差异和已有任务状态不会被安装包覆盖。

## 每次怎样推进

1. 开始时读取本计划，只选当前一个子项。
2. 给出具体方案和例子，集中讨论影响行为的少量问题。
3. 把结果写入对应设计文档，区分已确认、提议和待确认。
4. 达到本项完成依据后，更新本计划中的当前位置和下一项。
5. 说明本次变化、文件入口和仍未确认的内容，按现有规则提交和推送核对过的文件。

新增想法先放入对应后续步骤；确实影响当前基础设计时才提前处理，避免每次讨论都同时打开所有环节。

不设没有依据的日期或完成百分比。进度使用设计中、设计已确认、实现中、已实现待验证、验证通过等有证据的状态；创建文档不等于阶段验收。
