# asynctest-kb 信息获取与 Agent 接入引导

更新时间：2026-10-31。状态：设计草案，实际 Asynctest 界面待截图确认；未配置任何客户端、生成凭据或执行知识库操作。

## 用户明确的分工

主要引导用户在 Asynctest 的实际位置取得 MCP 连接信息并交给自己的 Agent。客户端适配交给当前 Agent 检查与处理，不默认用户使用 Codex。

用户提及 WorkBuddy、Codex 作为可能使用的客户端，同时表示尚不确定。它们只是候选验证对象，不是默认入口，也不表示当前已经验证兼容。

## 通用路径

1. 用户在 Asynctest 中进入实际的 MCP 连接信息入口。
2. 按服务要求选择项目、授权范围或获取凭据，并复制服务提供的完整连接配置。
3. 将复制的配置交给当前 Agent，说明希望接入哪个知识项目。
4. Agent 优先从运行上下文、可用工具和既有配置识别宿主，检查可用的配置方式并按授权接入；有可用连接时直接核对复用。
5. 配置后检查当前会话实际工具可用性，再用只读查询核对项目身份与可读内容，报告已验证的范围。

目前不写死第 1、2 步的按钮名称、菜单位置、传输方式或认证格式，这些需要截图或产品实际资料确认。也不提前编造各客户端的配置文件路径和菜单步骤。

用户可直接这样表达：

> 这是我从 Asynctest 复制的知识库连接信息，帮我接入，并确认能读取我要用的项目。

截图用于说明去哪里获取信息；真正接入优先使用用户复制的配置文本，避免依靠截图识别长地址或认证值。

## Agent 的适配责任

- 先检查实际宿主和当前能力，不假设所有 Agent 都能自动修改配置。能在授权范围完成时自行处理，保留已有连接和其他设置。
- 确需用户登录、授权或手动操作时，只说明当前必要的一步；宿主无法确定时再补问名称与版本。
- 用户交付连接信息用于接入，不等于授权创建、修改或删除知识内容。
- 读取配置不能证明当前会话已经能调用工具；工具可见也不能证明目标知识项目可读。验证结果分层报告，不只看全局开关。
- 验证连接优先采用指定范围内的只读查询；项目没有知识时如实报告已验证的项目读取范围，不为证明连接自动写测试知识。
- 认证信息按宿主提供的安全方式配置，仅留在约定的本机或受控位置，不写进通用 Skill、Git 或知识正文。
- 需要具体客户端说明时，再读取其适用版本的官方文档或实际界面。客户端附录按需增加，主引导保持通用。

教程需要字段和配置结构，不需要真实认证值。最终公开材料使用占位值和可替换示例，原始截图作为取证材料处理，不自动纳入公开包。

## 接入后的用途与边界

需求分析时读取适用历史知识，帮助补足概念、对象关系、现行规则和过去变更；不把召回结果直接当成本期已确认规则。

本期完成、正式上线且用户确认短期稳定后，强烈推荐将最终知识正文保存到 asynctest-kb。让用户知道收益：后续少重复解释、方便跨会话和人员交接、识别相关回归范围，并保留规则来源与版本。

知识库读取、连接配置、最终知识写入分别按实际范围推进。未接入时本地轻量记录仍可支撑当前工作；不将外部服务设为开始澄清的硬门槛。
