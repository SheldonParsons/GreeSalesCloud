# 3.2 页面取证与操作依据维护

更新时间：2026-11-02。状态：用户已确认调整后的 3.2 方案，待实施及行为验证。本次仅记录设计，不操作业务页面、不修改现有 UI 实现、不重打 Skill 包。UI 模块的最小内容、划分粒度和复用更新规则继续讨论，具体字段与目录不在本次固定为实现契约。

## 定位与两个目的

页面取证是贯穿测试过程、按需调用的能力。3.2 是设计章节编号，不是必须在用例编写之前全部完成的关卡。需求分析、用例编写或修改、QA 部署、正式测试和修复验证均可触发取证。

取证有两个目的：

1. 取得真实入口、控件、角色、状态、数据交接和结果观察位置，使用例操作步骤能够对应真实页面。
2. 维护项目 UI 资料及可复用模块，减少后续对稳定路径反复截图、回传整页和重新推理的开销，保留必要身份、目标及结果检查。

业务预期来自适用需求和确认规则；实际页面说明当前实现。取证不自动构成整套测试执行、业务通过或 BUG 提交授权。

## 用户说明与入口

用户随时可以问页面取证是什么、有什么作用、没有页面能否先写用例，以及为何旧页面需要再次核对。帮助入口路由到本说明，普通解释不启动浏览器、不索要账号或创建任务。

建议表述：

> 页面取证，就是到真实系统中确认：从哪里进入、点击什么、需要什么账号和数据，以及在哪里查看结果。它能让测试用例里的步骤更贴近实际页面，也能把已经核对过的重复操作保存为可复用模块，方便后续更快执行。页面还没上线也可以先写用例，等页面可访问后再补充核对；以后增加用例或页面发生变化，也可以随时重新取证。

面向用户的问答与 Agent 的详细规范按需加载，不要求用户学习模块字段或目录。帮助的设计路由见 [说明问答](../help-and-capabilities.md)。正式包内帮助与阶段参考在后续实施时同步，本次没有将设计文件当成已安装能力。

## 何时触发与怎样衔接

触发条件：当前工作需要真实页面信息，而已有依据不足、适用范围不匹配或已经变化。用户也可以在任何阶段明确要求补充取证；操作仍沿用本任务范围和授权。

| 时机 | 要解决的问题 |
| --- | --- |
| 需求分析中 | 页面辅助理解对象、入口或现行流程；涉及业务含义仍回到规则澄清 |
| 首次编写用例前或过程中 | 为缺失的关键动作取得真实依据 |
| 用户增加或修改用例 | 补采新场景涉及的独特入口、角色、状态或交互，不重走全部旧路径 |
| 新版本部署 QA 后 | 核对旧页面与新需求组合得到的步骤，修正暂定路径、控件和模块 |
| 正式测试或 BUG 复测中 | 核对页面变化、操作失效及新的必要分支 |
| 换环境、角色或平台 | 检查既有证据的适用范围，补足未覆盖条件 |

需求分析提供规则、场景骨架和未决问题；取证补足真实操作依据；用例编写把两者组织为独立场景。缺业务规则回到 3.1，缺操作依据调用 3.2，只处理受影响部分，保留已有成果。

## 页面未部署或平台首版

| 可用材料 | 如何推进 |
| --- | --- |
| 旧页面可访问，新功能未部署 | 用旧页面支撑沿用部分，以本期需求及原型支撑新增、调整部分，明确受改动影响的旧依据不能直接视为新版本实测 |
| 平台首版，没有任何真实页面 | 按需求和原型形成业务场景及暂定操作；缺失路径、控件或交互保留待核对，不能猜测后宣称可直接执行 |
| 新版本已部署 QA | 定向核对新增及变化部分，在授权范围同步用例步骤、页面资料和受影响模块 |
| 后续继续变更 | 保存前后版本与变化来源，检查引用关系，更新实际受影响部分 |

操作依据区分旧页面实查、需求或原型明确规定、暂时推导、新版本实查，并注明适用版本及来源。依据放在备注或关联记录中，正文保持可读；关键待核对步骤需能被执行者识别。

例如历史功能未部署时，可先复用已经确认的咨询列表查询与详情入口；新增历史区域的位置、名称及展开方式待补采。新页面的入口名称和交互顺序变化时修订操作；若应保留的历史内容缺失，则保留现象、核对规则或按适用流程记录问题，不改预期迁就实现。

QA 部署只提供新的页面取证条件，不等于正式上线，也不触发最终知识入库。业务理解、操作取证、执行准备、正式测试结果分别判断。

## 一次取证怎样进行

1. 读取本需求的范围、场景骨架、适用规则及现有用例或修改请求，定位本轮所缺依据。
2. 查询已有页面资料和 UI 能力，核对项目、系统、环境、版本、角色、状态及验证范围，确定可复用与需补采的部分。
3. 沿用已确认的账号、数据及操作授权；仅对影响本轮工作且无法查证的缺项补问。涉及创建、提交、审批等动作时核对是否已在授权范围，取得授权后不逐步重复询问。
4. 在实际工具能力内观察陌生路径，采集可见名称、导航、交互顺序、就绪条件、身份与数据交接和结果观察位置。页面动作由页面完成，网络证据可辅助定位，不替代被测 UI。
5. 根据差异同步操作依据，分别检查用例步骤及 UI 资料／模块需要怎样更新；没有真实依据时保留缺口，不登记为已验证模块。
6. 保存本轮证据、实际结束状态、数据处理情况、受影响产物与下一步。写入结果未知先核对，不盲目重放。

同一页面的多个边界场景可以共用操作依据；独特入口、角色、状态或组件差异需要分别核对。看到一张静态截图不足以证明完整交互；陌生交互不凭截图编造后续控件。

## 用例与 UI 模块的双向维护

每轮取证结束同时检查：哪些用例步骤、准备条件和数据交接可修正；哪些模块可复用、需要修订或值得新增。两类成果引用同一份取证依据，避免重复保存不同版本的事实。

页面资料、组件操作、业务动作、组合流程是逻辑层次，不要求每页建齐所有目录。先保存观察资料，再按复用价值形成可执行模块；不按每次点击、每条用例或需求编号复制实现。

已确认的模块设计方向包括身份与归属、适用范围、前置条件、输入输出、操作影响、执行与检查方式、异常处理和验证依据。下一轮继续讨论最小内容、划分粒度和复用更新规则，之后再确定机器可读契约及工具适配。

模块运行优先查索引、核对条件与版本、参数化执行已验证动作并返回简洁回执及证据入口。稳定路径减少重复视觉确认，身份、目标、关键跳转和保存回读仍保留检查。局部模块完成不自动更新整条用例或整轮测试结果。

遇到页面变化，返回实际失败位置及证据，补采后再修订和验证。不能为继续运行自动修改测试输入、跳过检查或用接口替代被测 UI。页面说明、未验证实现和限定条件下已验证的实现分别标识。

## 保存、复用与长期维护

- Skill 包保存方法、模板、规范及通用调用能力；项目保存页面资料和项目模块；跨项目共用实现保留单一来源及适用版本；需求保存本轮证据、数据和用例关联。
- 已有目录通过映射继续使用，例如本仓库的 ui-automation；不为候选目录树迁移或复制一套实现。具体结构待模块设计确定。
- 不按需求编号或环境复制整套代码；实际行为不同需明确适配和验证范围，不能仅换地址就继承通过结论。
- 记录项目、系统、环境、版本（未知注明）、角色、业务状态、实际路径、观察结果、证据和受影响场景。共用实现不保存某次运行的凭据、单号、浏览器 pageId 或快照 uid。
- 保存历史版本、证据及引用关系，更新只作用于授权的受影响产物；过去的执行结果保留原依据，不自动改为新版本通过。
- Skill 升级不能覆盖用户积累的项目资产。多会话按项目配置交接和维护，原有任务进度不因补采清空，具体模型和浏览器选择不写死为所有用户的要求。

## 何时停止本轮取证

针对本次目标，关键操作可定位，必要差异已核对，数据交接与结果观察位置明确，就可以停止已就绪部分的采样。剩余缺口明确影响范围和补充条件，不能为了宣称全量取证完成而删除未覆盖场景。

没有页面时可以完成基于材料的场景草稿，但页面取证仍记待补采；局部取证完成不代表所有入口或整套用例已可执行。取证中发现业务疑问回到需求澄清，发现操作依据缺失继续补采，正常推进不要求重做全部分析或正式测试。
