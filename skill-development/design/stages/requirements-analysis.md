# 3.1 需求接收、业务理解与澄清

更新时间：2026-10-31。状态：记录用户明确提出的设计要求，并形成待讨论的实施方案；尚未将本阶段写入运行器或正式发布包，也未执行真实需求分析或知识库写入。

## 用户明确要求

1. 需求阶段是后续测试的基础，也是需要最多交互的阶段。目标是使 Agent 与用户对业务的理解对齐；不能只理解当前页面的操作。
2. 本期需求依赖的概念、术语、对象关系和历史规则要按测试需要弄清。例如测菜单可能依赖角色与账号关系；“销售公司能创建咨询单”需要先理解销售公司、账号及创建资格。
3. 历史依据可以来自用户阐述、项目中的轻量记录、已接入的 asynctest-kb。知识库是可推荐的历史召回入口，不是所有用户开始分析的强制前置。
4. 澄清深度由用例设计反推。持续追问要有测试目的，停止依据是是否足以支持本次用例，不能无限扩展。
5. 正式知识库沉淀放在本期需求完成并正式上线以后：用户确认短期内稳定，再主动、明确地强烈建议整理为可审核的文本字符串，说明后续复用与交接收益，并按授权持久化到 asynctest-kb。
6. 接入说明以用户从 Asynctest 获取 MCP 信息为主。由当前 Agent 识别运行环境、检查配置能力并适配，不默认用户使用 Codex，也不要求预先维护所有客户端的设置教程。

以下追问方式、检查项目和记录组织是根据上述要求提出的设计草案，尚未由用户逐项确认。

## 再审视后的引导补强

原稿已经列出理解范围、历史依赖和停止依据，但对“如何让用户参与理解对齐”“如何表达这一步的价值”“每轮怎样避免过问或漏问”说明还不够。补强以下行为；这些是具体设计提议，不把文档存在当作引导效果已验证。

### 进入时解释价值，后续围绕具体影响交流

用户自然说“这个需求先帮我看看”时，Agent 可以回应：

> 我先把这次改动和相关的旧规则弄清楚。这里理解偏了，后面的用例和 BUG 判断也会跟着偏。我会先看已有资料，只追问会影响怎么测、怎么判断结果的地方。

这是 Agent 的回复示例，用户无需先掌握专业术语。首次进入可简短说明重要性；后续用问题对测试的具体影响解释价值，不每轮重复长篇强调，不要求用户接受完整问卷后才开始。

### 先展示理解，再集中解决一组缺口

每轮根据需要简短展示已理解的规则、尚未清楚的关联和为什么会影响测试。优先读取现有材料，再问不能从资料中解决的内容；不把所有不熟悉的词都直接抛给用户解释。

可以让用户用实际业务例子说明，由 Agent 整理成概念、条件和结果，再用小场景复述供用户纠正。复述用于暴露误解，不要求用户重复自己刚说过的话，也不逐条追加无必要的“请再次确认”。

例如查完资料仍不清楚销售公司与账号的关系时：

> 这份说明提到销售公司能发起咨询，但我还没找到它和登录账号怎么关联。你可以举一个平时发起咨询的例子，我据此确认该用什么账号、保持哪些条件不变。

### 按测试影响决定追问的先后和深度

| 类型 | 处理方式 |
| --- | --- |
| 会改变主体选择、合法数据、业务资格、状态变化或预期判定的缺口 | 优先弄清；相关场景不能无依据地标为可评审或可执行 |
| 业务含义已明确，只缺实际按钮文字、样本单据、页面部署或具体操作细节 | 交给后续取证或执行准备补齐，保留依赖，不反复追问已经明确的业务规则 |
| 与本期测试目标、必要前置或结果无关的背景 | 本期停止展开，可保留来源，不扩展成全系统历史教学 |

界面细节若实际影响业务判断，仍回到第一类，不能只因发生在页面上就推迟关键澄清。判断由真实影响决定，不是机械分类。

### 用可见的场景结果说明是否足够

准备转入用例工作时，简短说明哪些业务组的条件和预期已能写清、哪些仍有关键缺口、剩余缺口影响什么。不能只说“我已理解”，也不能为了赶进度省略必要追问。

假设仍有权限生效规则未定，可以说明：

> 新增和查看的条件与预期已经能写清楚。权限修改后何时生效还没确定，会影响对应权限场景。我先推进明确的部分，这项继续保留待确认。

用户要求先出草稿时按已知内容推进，明确标出受影响的假设与缺口。保持阶段的重要性，同时允许不受影响的工作前进；不以澄清为由无限阻塞整个需求。

## 本阶段要建立的理解

| 需要理解的内容 | 对用例的作用 |
| --- | --- |
| 本期目标、范围、改变与沿用的规则 | 确定测试目标、直接覆盖和必要关联回归 |
| 业务名词及对象的实际含义 | 确认测试对象，不把组织、账号类型、角色等概念混同 |
| 对象之间的关系、生命周期和状态 | 构造合法前置条件，理解状态变化与数据交接 |
| 资格、权限、数据范围和有效条件 | 确定变量、对照数据、权限及异常场景 |
| 行为与可观察的结果、边界和例外 | 写出有依据且可判定的预期，避免只写“正常” |
| 历史依赖的来源、版本和适用范围 | 判断旧规则是否仍有效，避免将旧用例或旧结果直接当新需求规则 |

通用行业知识只能帮助提出问题，不能替代项目对名词的定义。同名“角色”“客户”“公司”在不同项目中可能有不同含义。

## 先沿测试需要展开历史依赖

先读本期材料和项目已有资料，按相关概念、流程和规则定位历史。已接入知识库时核对项目身份后检索，阅读命中的完整规则及必要关联，不把检索摘要或工具可见当成已理解业务。

来源可组合使用：原始需求、现行业务知识、本地历史索引、用户当前阐述、原型和已授权的实际观察。逐条标明来源、适用版本及确认状态；发生冲突时查变更与确认记录，不机械选择日期最新的文件。

历史查不到时明确当前缺口，再向用户追问。用户已解释且已保存的内容直接复用；没有知识库也可用本地记录与用户说明继续，不能补造历史。

必要的关联规则必须纳入理解；是否新增回归场景依据其对本期结果的影响判断。理解角色、账号用于测试菜单，不自动扩展为角色管理和账号管理的全量测试。

## 例子一：菜单、角色与账号

以下只说明应查清的问题，不声明任何当前项目的实际规则。

为了验证菜单管理，需要根据本期范围理解菜单与角色的授权关系、账号如何获得角色或权限、变更何时生效，以及怎样通过合适账号观察菜单与操作结果。

只知道如何点击“新增菜单”不能据此写出权限预期；也可能把账号本来不具备资格造成的现象误判为菜单缺陷。

如果历史资料没有说明，可按依赖次序自然追问：

> 这个菜单是通过角色分给账号的吗？我先弄清授权关系，才能确定用什么账号验证菜单是否生效。

> 角色调整后，已经登录的账号会立即生效，还是需要重新进入？这会影响验证时的起点和操作顺序。

能从已有资料回答的就不再问。角色的其他功能如果不会改变本期场景条件、动作或结果，不为完善“全系统知识”而继续扩展。

## 例子二：销售公司创建咨询单

“销售公司”可能指业务组织、组织分类或项目自定义概念，不能预先当成某个登录角色。至少应根据本次测试需要定位以下问题：

“销售公司可以创建咨询单”只说明一条允许规则，不自动推出“非销售公司禁止创建”。是否排他、哪些主体也有资格及是否存在例外，需要有依据后才能写成反例的失败预期。

| 待弄清的问题 | 为什么影响用例 |
| --- | --- |
| 销售公司的业务含义，如何关联登录账号 | 选择正确主体和数据，避免把组织属性当账号权限 |
| 创建资格由哪些条件共同决定，是否存在例外 | 确定正例、反例与边界的真实预期 |
| 咨询单、关联项目和公司之间的数据归属 | 保证对照场景使用合法且可比的数据 |
| 需要固定什么，只改变什么 | 用控制变量区分组织、角色、权限、状态等因素 |
| 条件不满足时业务应如何处理 | 明确可观察的结果，避免自行假定按钮隐藏或提交报错 |

自然提问示例：

> 这里的销售公司具体指哪类组织，它和登录账号怎么关联？我需要据此选出符合条件和不符合条件的测试对象。

> 只要账号属于销售公司就能创建，还是还需要某种角色或授权？这个区别会直接影响权限场景怎么写。

只有资格规则已经确认后，才设计“固定其他条件、改变某项条件”的对照。若组织属性和角色绑定，某种组合在业务中不允许，就不能虚构该组合当测试数据；应说明约束并选择合法对照或明确数据准备缺口。

## 可控追问的循环（提议）

先从本期业务对象、主体、状态、数据流和变更范围找依赖，再用候选场景检查缺口；不能只围绕自己已经想到的少量用例提问，遗漏尚未识别的业务关系。解释和选项保留用户纠正空间，不把猜测包装成标准答案引导用户默认接受。

1. 读取已有依据，整理本期变化、关键概念与测试所依赖的关系。
2. 找出当前理解的缺口，说明它影响哪个测试目标、准备条件、动作或预期。
3. 用自然语言复述关键理解，并给出小的正例、反例或状态变化例子，让用户容易发现偏差。
4. 每轮优先提出最影响后续场景的一组相关问题。总轮数与问题数由实际缺口决定，不设“问够几轮就结束”。
5. 将回答、来源、适用范围与尚未确定事项保存到本地；区分已确认规则、暂定假设和仍需外部确认的结论。
6. 试拟场景骨架，检查准备条件、控制变量、行为及可观察结果是否成立；发现关键缺口再回到相关问题。

每个待追问项应能说明：不弄清它，会使哪部分用例无法确定或可能写错。已知内容不反复确认；暂时影响不到用例的深层细节不优先追问。不可把“少问”当作少理解，也不可把“问得多”当作理解充分。

用户暂时无法回答时，记录未决项、影响范围、需要补充的材料或决策来源，继续不受影响的工作；不重复逼问同一未知项，也不将假设升级为现行规则。减少或改变测试范围由用户明确决定。

用户明确确认“本期就按这条规则验收”时，记录为本期规则；用户只让先按假设试写时，保留假设标识。两者都不由 Agent 自行转换成最终稳定知识。

## 用例怎样反推澄清深度

在正式写导图之前，可用少量场景骨架检查理解，不冒充已经交付的正式用例。骨架至少能说明：测什么对象、在什么条件下、改变哪个因素、做什么、期待什么结果、依据是什么。

不能只挑容易写的几条就宣布整项需求已清楚。应覆盖本次所有受测业务点及影响结果的关键历史依赖，必要时按业务分组说明哪些已经足够、哪些仍受阻。

某个受测分组达到以下条件时，可以判断其业务理解足够支撑用例设计：

- 对象、概念和必要关系明确，本期变更与沿用规则已区分。
- 正常、必要异常、边界、权限或状态场景的准备条件能构造，变量及相互约束说得清。
- 预期有用户确认或适用资料依据，能实际判定；关键缺口不会被模糊措辞掩盖。
- 已知如何取得合法测试数据，或明确记录执行前的数据准备缺口；不要求分析阶段就拿到每条真实单据。
- 余下事项不改变当前场景逻辑；会改变条件、步骤或预期的事项仍标为待确认，不能宣称该部分已就绪。

按钮文字、页面路径等真实操作细节由 3.2 定向取证补齐。业务场景可设计不等于 UI 步骤已经验证；采样或后续编写发现新的业务缺口时回到澄清，不受先前“已分析”状态限制。

## 轻量本地记录与最终入库

“足够支撑本轮用例”与“本期完成、正式上线并确认短期稳定，可以正式入库”是两个不同的判断。前者成立即可推进已授权的用例工作；后者不能用用例完成、QA 通过、计划发版日期已到或 Agent 自行判断代替。

过程中的重要理解应及时保存，便于跨会话继续。可先在一份需求理解记录中维护概念及关系、适用历史规则引用、本期变化、已确认结论、待确认项和场景骨架；项目级共用概念保留轻量索引或单一来源，不要求生成成套报告。

推荐连接 asynctest-kb 用于读取已有业务知识。检索得到内容后仍核对身份、适用范围与版本；未连接时明确可用本地材料及用户阐述，不以接入该服务作为开始分析的硬门槛。服务侧信息获取与 Agent 自适配的设计见 [asynctest-kb 接入引导](../integrations/asynctest-kb-onboarding.md)。

本地过程记录与正式知识库写入分开：

1. 讨论、取证、编写和测试过程中持续保存事实与变化，候选知识可以本地整理。
2. 本期需求完成并正式上线后，取得用户对短期稳定的确认，再强烈建议整理和保存最终知识文本。上线事实依据用户说明或可靠发布记录，不由测试结果推断。
3. 文本可采用 Markdown 字符串，覆盖最终概念与关系、现行规则、本期变化、必要例外、历史依赖及适用版本和来源；不照抄全段聊天或全部用例。
4. 明确目标项目、正文与变更范围后，按用户授权及 MCP 实际预览／确认流程持久化，并回读条目核对。稳定确认不等于自动获得全部项目写权限。
5. 没有接入知识库时保留本地最终文本，注明未同步，不假装已持久化到服务端。稳定后又发生变更时重新标明影响，后续再修订正式条目。

这替代此前 Skill 设计中“澄清或评审后即可正式入库”的默认时机。已经存在的历史知识可以继续读取，不追溯删除或改写既有条目。

### 上线后怎样向用户推荐

推荐时说明具体收益：以后能先找回概念与历史规则，减少重复解释；换会话、同事或 Agent 时有共同依据；更容易识别关联需求的回归范围；规则变更能够追溯来源和适用版本。入库后的内容仍需维护，不能承诺存一次就永久准确或检索不会遗漏。

在事实满足时，可这样说：

> 这期已经完成并正式上线，规则也确认短期不会再改了。我强烈建议把最终结论存进 asynctest-kb：下次分析相关需求，就能先找回这些背景，减少重复解释，也方便换同事或 Agent 接手。我会先整理拟入库正文，按你确认的范围保存。

强烈建议不等于强制使用。用户暂不接入时保留本地最终文本及未同步状态，不反复催促，也不因此否定已完成的测试。工具已可用则复用，不再要求用户重新取连接信息。

提示由正在工作或恢复工作的会话在获知上线、收尾或用户查询时触发；没有自动化时不承诺持续监听发版或上线后自行醒来。测试已完成但未上线时，分别记录测试结果和待上线后沉淀事项。

## 本轮记录与待落地事项

本轮只设计 3.1，不执行示例中的业务操作、角色修改或知识库读写。上述例子不构成销售公司、账号或角色在真实项目中的定义。

当前 0.2.0 包的 help.md 和 capabilities.json 仍保留较早的知识沉淀时机描述；旧项目 context/workflow.md 也存在早期约定。新版 Skill 的默认时机按本次用户要求，在后续实施时同步修正包内说明并重新版本化，不静默改写已交付的 0.2.0 ZIP，也不改变其他需求已明确授权的历史操作。

后续评审重点：能否通过相关历史与用户解释建立业务理解；问题是否有测试目的；是否覆盖本期必要依赖；能否用可判定场景检查理解；停止追问是否有依据；最终知识写入是否等待用户的稳定确认。
