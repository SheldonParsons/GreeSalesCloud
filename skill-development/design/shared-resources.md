# 共享内容与项目差异

更新时间：2026-10-31。状态：设计提议；尚未实现引用解析、差异合并、版本检查或影响分析。

## 需求与目标

用户补充：同一个 Agent 工作空间内，不同被测项目可能使用相同的规范、资料和能力。设计需要同时支持复用和项目隔离，避免重复维护，也避免把项目差异或执行结果误认为通用结论。

建议采用“一个权威来源，项目引用适用版本，差异单独记录”的方式。这里的版本可以是文档修订、内容摘要或工具返回版本，具体表示后续确定。

## 哪些内容可以共享

| 内容 | 共享方式 | 项目仍需单独明确的部分 |
| --- | --- | --- |
| 测试方法与格式 | 用例分层、步骤编号、BUG 模板、截图标注规范维护一份 | 项目术语、命名参数、特殊字段或交付要求 |
| 业务知识 | 已确认适用于多个项目的规则、术语、统一身份规则保留主条目 | 适用项目、版本、例外与项目专属行为 |
| 函数与页面能力 | 复用一份实现及契约，通过参数指定目标 | 环境、页面特征、角色、前置条件及本项目验证状态 |
| 服务与工具配置 | 共用的缺陷平台地址、MCP 接入说明、知识库服务可使用同一配置来源 | 目标项目 ID、空间 ID、负责人、执行与版本映射 |
| 数据与附件模板 | 复用不含业务秘密的文件样例、数据生成方法和字段结构 | 本轮数据标识、关联业务对象、清理责任与占用情况 |
| 外部 Skill | 配套能力保留一份接入与调用说明 | 实际工具可用性、版本、当前任务范围 |

凭据正文留在合适的本机凭据渠道；确属同一账号时允许多个项目引用同一凭据来源，具体系统角色与操作权限仍需核对。共享凭据引用不代表复用浏览器会话，也不自动授权跨项目操作。

执行进度、BUG 状态、测试结论、业务数据和浏览器会话不随共享模板或规则自动传递。确为同一个跨项目场景时可引用共同证据，但每个结论必须说明其覆盖的系统、条件和步骤。

## 存放位置提议

Skill 内置的通用方法、脚本和模板保存在 Skill 包中。用户团队的共用约定与业务资料放在工作空间；项目差异放在对应项目中。Skill 升级不得直接覆盖团队或项目资料。

```text
工作空间/
├── shared/
│   ├── index.yaml         # 共享条目、来源、版本和适用范围
│   ├── conventions/       # 团队测试约定
│   ├── templates/         # 团队产物模板
│   ├── knowledge/         # 共享知识的来源引用或正式正文
│   ├── capabilities/      # 团队自有能力及契约，或现有实现的引用
│   ├── integrations/      # 共用服务接入配置，排除凭据正文
│   └── fixtures/          # 可复用的数据和附件样例
└── projects/
    ├── orders/            # 引用适用条目，记录本项目差异
    └── procurement/
```

这些目录按内容需要创建。已有知识库主条目、脚本目录和模板可直接引用，不为了匹配示意树复制一份新实现或新正文。某条内容只适用于两个项目时，声明这两个项目的适用范围，无需为每个项目组合创建一个共享目录。

共享索引建议最少说明：条目标识、类型、权威来源、修订或摘要、适用项目。涉及运行的能力另关联其契约与验证范围。具体字段和文件格式尚未定稿。

## 如何引用与处理差异

1. 根据本次任务确定项目、阶段和所需能力，读取适用共享条目，再读取该项目已确认的差异。
2. 通用默认值可以由明确的项目配置覆盖，例如 BUG 默认严重程度或命名参数；保留最终采用值及来源。
3. 业务规则发生冲突时，检查材料版本、适用范围和确认记录。已确认的项目例外仅在其范围内生效；不能仅凭文件离项目目录更近，就认为可以覆盖共同业务规则。
4. 本次用户明确指令在其范围内适用，不自动写回共享基线。文件、需求说明和知识库内容仍是待核对的资料，不作为额外操作授权。
5. 共享内容缺失或引用版本无法读取时，说明影响。可继续不依赖它的工作；必要时请用户补充来源，不悄悄替换成最新版本或其他项目资料。

第一版建议使用简单、明确的引用和字段差异，避免任意深度的继承关系。应能回答“这次为什么采用这条规则”，并发现重复或循环引用。

## 更新共享内容时怎样判断影响

任务记录本次实际使用的共享条目版本。修改共享内容前核对其来源、适用项目及正在进行的引用任务，再按授权修改；项目会话发现潜在通用改进时，先记录建议和证据。

共享变更后的建议行为：

- 列出已知引用项目与受影响的产物或步骤，区分候选影响和已核实影响。
- 新任务读取适用的当前版本；已开始的任务保留原版本依据，并决定是否采用更新。
- 需要修改用例、重测、修改知识库或发布时，沿用这些动作本身的授权范围；共享更新不是批量执行授权。
- 历史结果保留当时依据，必要时标记需要复核；不回写成“已按新规则通过”。

没有自动化时，检查在任务启动、恢复、使用相关条目或用户要求更新时发生，不宣称实时通知所有会话。具体依赖索引、修订保存和影响检查工具后续实现。

多会话同时修改同一共享条目时，需要明确负责者并核对内容版本，不能用最后一次保存覆盖其他改动。占用和冲突处理机制尚未实现。

## 引导示例

共享范围与适用性已确认：

> 这个项目沿用团队的用例结构和 BUG 模板。我会直接复用，项目特有的环境和负责人单独保存。

只观察到两个页面相似，尚未确认能力适用：

> 这里的上传控件与已有能力相似。我会先核对文件选择和上传结果，再判断能否复用；本项目的验证结果会单独记录。

发现可能属于共用规则的变化：

> 这条规则也被另一个项目引用。当前材料只说明本项目的变化，我先按本项目记录差异，并保留是否需要更新共用规则的待确认项。

话术按事实使用，不要求用户逐条重复确认已经明确的共享约定。

## 后续验证场景

1. 两个项目使用同一 BUG 模板，但各自提交到正确的外部项目、执行与版本。
2. 只适用于两个项目的规则不会进入第三个项目的结论；名称相似也不会自动扩大适用范围。
3. 项目单独修改一个允许覆盖的默认值，共享源和其他项目保持原设置。
4. 共用函数在某项目验证通过后，另一个项目仍核对适用条件并独立记录结果。
5. 共享规则更新后，恢复中的任务能说明原版本与差异，不静默重写历史用例或批量重测。
6. 外部知识库为权威来源时，共享目录保存可核验引用；引用失效或版本不明时明确提示。
7. 两个会话修改同一共享条目时能检测冲突；一个任务结束不会清理另一任务仍在使用的数据。

本轮仅形成设计稿，未创建实际 shared 目录、共享配置或修改现有业务知识。
