# 多项目隔离与任务状态

更新时间：2026-10-31。状态：设计提议；尚无运行时隔离、并发控制或状态恢复实现。

## 用户提出的使用场景

一个 Codex、WorkBuddy 或其他 Agent 的项目中，用户可能同时测试多个业务项目，也可能分别开会话推进。因此不能将 Agent 工作空间直接视为唯一的被测项目。

本文件记录对该场景的设计回应。目录名、配置字段、状态格式、任务绑定及资源占用机制均待细化和验证，不将助手方案直接视为用户已确认的实现。

## 四层身份

| 层级 | 含义 | 示例 |
| --- | --- | --- |
| 工作空间 | Agent 打开的逻辑工作范围，映射到已有本地目录或获授权存储 | 一个承载多项测试的 Agent 项目 |
| 被测项目 | 独立维护业务资料、环境和工具映射的项目 | 订单平台、采购平台 |
| 系统或端 | 被测项目内具体访问的系统 | 客户端、管理端、接口服务 |
| 需求与任务 | 项目中的需求，以及需求内可分配的具体工作 | 需求 12345；查看场景取证任务 |

项目的显示名称可以变化，内部使用稳定标识。需求以“工作空间标识 + 被测项目标识 + 需求标识”定位；不同项目允许存在相同需求编号。独立执行任务另有任务标识，具体字段命名待定。

这些是 Skill 管理工作的逻辑层次，不假设各宿主产品原生提供相同的项目结构或 API。

## 目录与状态归属

新工作空间的示意：

```text
工作空间/
├── workspace.yaml
├── shared/
├── projects/
│   ├── orders/
│   │   ├── project.yaml
│   │   ├── context/
│   │   └── requirements/12345/state.json
│   └── procurement/
│       ├── project.yaml
│       ├── context/
│       └── requirements/12345/state.json
└── .local/
```

项目索引保存稳定标识、名称、资料位置等必要信息。每个项目维护自己的系统、环境、工具目标和产物路径。每项需求独立保存各阶段状态、当前任务、产物版本、未完成事项和下一步。

现有目录通过映射接入，不自动搬迁；外部正式用例或 BUG 文件仍可保留原位置。明确共享的方法和模板放在 shared 或使用引用；各项目的业务规则默认保留各自来源与适用范围，跨项目使用需有明确关联。

状态与证据关联，不能仅改一个阶段字段就表示工作完成。用例评审、执行、BUG 复测和知识同步可以同时处于不同进度。人可读摘要与结构化状态需要一致的更新机制，具体机制尚未实现。

## 每个会话绑定自己的任务

不使用可被任意会话改写的全局 currentProject 来决定后续动作。

每次操作从本次明确指令、当前会话任务绑定和已核对的产物定位项目。绑定至少关联项目、需求、任务及当前授权范围；运行浏览器时还需系统、环境、角色和资源引用。宿主会话 ID 可作为辅助关联，宿主没有该能力时通过任务标识与交接资料恢复。

用户只说“继续 12345”，且两个项目都有这个编号时，先利用明确的会话上下文定位；仍有歧义才询问所属项目。默认项目可用于新任务的建议，但不覆盖已有会话绑定。

同一会话可以切换任务，切换时保存当前进度并明确新归属；其他会话不受影响。同一项目的多个执行者写自己的运行记录，由明确的负责者汇总需求状态。具体更新冲突检测、版本检查与资源占用机制另行设计。

## 需要隔离的对象

| 对象 | 设计要求 |
| --- | --- |
| 需求、用例、BUG 与证据 | 路径或引用携带项目归属，重名文件和同号需求不能相互覆盖 |
| 环境和账号 | 按项目、系统、环境、角色选择对应引用；相同用户名不代表相同身份 |
| 知识库与缺陷平台 | 每个项目有显式目标映射；业务项目名称不必等于外部平台项目名称，写入前核对实际对象 |
| 业务规则与检索 | 默认检索当前项目范围，共享或跨项目规则带来源、版本与适用范围 |
| 浏览器状态 | 按项目、环境及角色选择可隔离的浏览器上下文或配置；同一浏览器的不同标签页不保证登录态隔离 |
| 页面和导图 | 明确当前操作者，调用时核对目标文档或页面；同一资源的互斥写入需协调 |
| MCP 或脚本 | 调用携带具体目标；只有全局当前目标的工具须串行使用并回读身份，不假设 MCP 自带项目隔离 |
| 共享函数 | 复用实现，运行参数与临时数据按任务保存，不能缓存一个跨项目共用的当前账号或目标 |

若宿主或工具不能提供所需隔离，应说明限制，协调为顺序执行或等待资源可用；不能仅根据目录已经分开就声称页面状态隔离成功。

这些设计用于防止测试资料和操作串项目，不构成安全租户边界。对不同用户的文件访问或服务权限隔离仍依赖宿主、文件系统和服务端权限，Skill 文档无法强制保证。

## 跨项目需求如何处理

一个业务需求可能真正涉及多个被测项目，例如统一身份平台、CRM 和订单平台共同参与单点登录。

建议为该需求明确一个牵头项目，保留唯一的需求主记录和正式用例集合，声明参与的项目、系统及边界。其他项目通过引用关联到它，不复制出多份独立状态。牵头归属不明确且影响保存或外部写入时，需要用户确认。

跨项目场景的每一步注明实际系统、角色、数据交接和结果。调用环境、账号、知识库或缺陷平台时按该步骤的真实目标取配置；牵头项目不自动决定全部 BUG 的所属项目。

单点登录等场景可能需要多个系统共享浏览器上下文，应显式建立本任务的协作范围。该共享属于本场景的被测链路，不扩展为其他会话共享登录态的默认许可。

## 后续需验证的行为

1. 两个被测项目各有需求 12345，创建用例和更新状态均只影响目标需求。
2. 两个会话分别处理不同项目，一个会话切换项目后，另一个继续使用原绑定。
3. 相同账号名、同域页面或共用 MCP 时，不误用登录态、工具当前对象或文档。
4. 外部缺陷平台的实际项目映射与业务项目名称不同，仍能核对并选择正确目标。
5. 跨项目需求只维护一份主状态，各系统步骤和 BUG 目标能够追溯。
6. 已发出但结果不明的写操作在恢复时先按原项目、任务及数据 ID 回查，不向新项目重复提交。
7. 现有目录与外部文件可通过引用接入，项目更名不破坏需求身份和历史证据关联。
8. 两个执行者同时申请同一页面或导图写入时，能避免互相覆盖，并支持明确交接后的继续。

上述为未来实现的验收场景，本轮没有执行业务测试。下一步应先确认项目身份与跨项目需求的组织方式，再细化状态字段、绑定生命周期和资源协调方法。
