## 用途与入口

用户可以先了解 Skill，也可以直接开始已有任务。说明问答在首次使用和工作中都可进入，不作为启动任务的强制前置步骤。

| 请求意图 | 处理方式 |
| --- | --- |
| “这是什么”“能做什么”“流程怎样” | 直接回答相应说明；无需先收集项目、账号或完整材料，不因提问创建任务或改进度 |
| 活跃工作中插问使用方式 | 先回答，保留任务与状态，再继续原来已授权的工作；不把插问当取消、暂停或重启 |
| “能帮我把这个需求写成用例吗”等带明确对象的行动请求 | 结合语境按任务处理，不因问句形式只回答“可以” |
| 同时要求介绍和开展具体工作 | 先简短解释，再执行明确授权的部分；缺少影响下一步的信息才补问 |

已经明确暂停的任务不会因一般问答自动恢复。遇到用户要求停止或更换目标时遵循新指令。

## 三个核心问题的回答示例

### 这个 Skill 是什么

> 这是一个面向 Web 测试工作的协作 Skill。它帮助你组织项目资料、需求进度和测试记录，按约定开展工作，也方便换会话或交接给其他人后继续。
>
> 你可以直接说明眼前要做的事情，不需要先学习它内部的目录或配置格式。

先用日常语言说明定位，再按用户追问解释技术细节。无需在每次介绍中罗列全部文件、函数和工具。

### 这个 Skill 可以帮助我干什么

回答依据当前版本及已验证能力。以下保留基础能力的说明示例：

> 当前版本已经能管理多个被测项目、复用共用规则、保存需求进度和任务记录、登记协作分工，以及留存资料快照和进行本地备份恢复。
>
> 需求分析、页面取证、用例编写、实际测试、BUG 提交与修复验证，是后续正在逐步完善的工作环节。真正操作页面或外部平台，还需要对应工具及本次任务授权。

事实来源为本包的 [能力说明](../skills/qa-workflow/assets/capabilities.json)。以后读取实际安装版本的说明，不永久固定为此示例；计划、代码存在、工具可见和业务验证通过分别表达。

### 这个 Skill 的流程是怎么样的

解释用户开展测试的业务流程。除非用户询问开发进度，不把本仓库的八步研发路线当成使用流程。

> 整体工作通常从理解需求开始，明确业务规则，再核对页面、编写和评审用例。之后按范围执行测试，记录和提交已确认的 BUG，修复后验证，最后整理交付与未完成事项。
>
> 过程中的结论会持续记录下来。这期完成并正式上线、你确认短期内稳定后，我会强烈建议把最终概念和规则存入 asynctest-kb，方便下次找回背景、少重复解释，也方便交接。你也可以从已有用例或待验证的 BUG 接入，本次只推进指定范围。

上述是完整目标流程，当前实际支持范围须结合版本说明。使用者只问流程时不自动开始其中的业务操作。

## 回答方式与事实维护

- 先回答用户问的点，必要时给一个贴近任务的例子；用户问概览时用简短分组，问细节时再展开。
- 不要求用户先给需求编号或账号，才能知道 Skill 是什么。
- 不把普通能力问题引导为配置问卷；可说明开始方式，但不强制用户立刻提供材料。
- 介绍总体定位、当前可用能力和后续计划时分清边界，避免把规划中的完整自动化描述为现有功能。
- 通用说明按需读取对应参考内容；问当前能否在某环境执行时，才核对本次需要的实际工具和条件。
- 能力发生变化时更新统一版本说明，问答引用同一来源，减少多处写死答案后的漂移。
- 必要说明已随 Skill 包提供，包内帮助不依赖当前仓库的内部设计文件；内部设计只保留决策依据。
