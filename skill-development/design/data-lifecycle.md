# 长期维护与信息保全

更新时间：2026-10-31。状态：用户已明确长期使用与信息保全目标；以下措施为 1.5 讨论方案，尚未实现归档、备份、恢复或升级迁移。

## 目标与已有设计的覆盖

用户要求：随着项目资料增长仍能长期使用，保留信息；后续所有规划都要考虑这一点。

1.1 提供稳定归属和引用，1.2 提供单一来源与版本边界，1.3 提供工作状态和中断恢复，1.4 减少并发覆盖与重复操作。这些是基础，还需补充长期检索、原始依据留存、归档、独立备份、恢复演练及格式升级。

目标落实为可检验的结果：已确认的重要信息落到可持久读取的资料中；历史版本与证据可定位；备份覆盖明确且经过恢复验证；数据增长后读取仍按需进行；升级保留用户资料。

Skill 无法单独保证设备故障、外部服务变化或未保存动作绝不造成丢失。应明确最后保存与备份恢复点、未覆盖范围和实际验证记录，不能把“已同步”当作永久保全保证。

## 1. 资料落盘与依据留存

- 重要需求材料、确认结论、规则变化、用例版本、执行结果、BUG 和知识关联及时保存，不依赖聊天历史作为唯一来源。
- 摘要用于定位与理解；原始材料、重要决策依据和证据保留可追溯版本，不能仅留 AI 压缩摘要。
- 跨项目共享条目保留来源、适用范围和变更关系；当前有效规则与历史规则清楚区分，不能直接覆盖历史依据。
- 外部导图、知识库、文档和 BUG 链接可能失效。应登记来源、时间和版本，并在实际权限及用户范围内保存必要的可恢复导出或快照；仅有 URL 不表示内容已备份。
- 外部资料快照用于留存，不伪装为现行权威版本。新工作仍核对当前来源及差异。

## 2. 资料增长后的检索与归档

按工作空间、被测项目、需求及运行批次组织资料。入口保存简短状态和索引；Agent 先定位当前任务，再展开相关规则和证据，避免每次读取全部历史。

已结束需求可先通过归档标记退出默认活跃视图，保持稳定位置及可检索入口。归档不删除原始资料，不改变仍未解决的 BUG 或未测项，不使未完成需求变成完成。

例如使用数年后已有数百项需求，继续 71652 时只加载其状态、适用规则与相关运行记录；查询某次历史咨询规则时，仍能定位当时来源、导图版本和证据。上述数量是验证规模示例，不是当前实际统计。

索引和缓存应可从权威记录重建，不能成为信息的唯一副本。第一版优先采用文件、稳定引用和按项目分层的索引；是否需要更复杂存储由实际规模及性能证据决定。

## 3. 备份覆盖与恢复

先建立产物清单，列清实际存放位置、敏感性、恢复方式和备份覆盖，再选择适合的目标及频率。

| 内容 | 必须核对的保全范围 |
| --- | --- |
| 已确认规则、设计文档、配置、状态记录 | 版本历史、远端或独立副本、可恢复的配置格式 |
| 正式思维导图及附件 | 实际外部文件位置、原生格式与必要可读导出、附件关联 |
| 本地 BUG 与截图 | 正文和引用图片均在恢复范围内，不能只备份 Markdown |
| 知识库与在线需求资料 | 来源与版本记录，授权范围内的可恢复导出；核对服务端与本地覆盖的边界 |
| 本机私有数据 | 有恢复需要时使用用户认可的私有存储和访问保护；凭据与公开代码分开管理 |
| 可再生缓存或临时产物 | 明确可再生条件及保留策略；待核实操作和唯一证据不能当缓存清理 |

本项目的正式导图、BUG 和部分证据可能位于仓库之外；只提交当前仓库不能证明这些文件已备份。被 Git 忽略的 .local/ 也不自动获得备份保护。具体备份目标、权限、频率、保留期和可接受恢复点后续确定，本轮不复制或上传任何私有资料。

版本控制用于追溯已纳入的文件，远端同步用于保存对应提交；仍应有覆盖必要文件的独立恢复副本。同步可能传播误删，因此需要可恢复的历史，而不能只依赖实时镜像。

备份完成后核对清单、完整性及实际恢复能力，记录最近成功的备份和恢复演练时间、覆盖版本和缺失项。只有实际恢复过，才能说明对应范围在该恢复点可找回。

## 4. 写入、删除与升级

关键结构化文件写入应检测版本冲突，并具备中断后保留旧有效版本的机制；保存后回读核对。文件、MCP 和外部系统无法视为一个天然原子操作，分别记录结果与待同步部分，沿用 1.3 的未知结果处理。

历史产物默认不因时间久或为了减少 token 自动删除。整理与摘要不能覆盖唯一原文。清理政策、删除范围和恢复方式需要明确；任何活跃任务引用的内容先检查依赖，不能静默删除。

Skill 版本与用户数据格式分别管理。升级前准备可恢复副本与具体迁移说明，在副本上核对条目、附件和引用完整性后再迁移；失败保留原数据并有回退路径。只有旧数据兼容性核验通过，才能宣称升级保留了原资料。

## 5. 检查时机与自然引导

在任务启动或恢复、阶段收尾、归档和升级等实际触发点，对相关范围检查资料和引用；全量校验与恢复演练按后续约定执行。没有调度机制时不承诺定时备份、后台巡检或主动唤醒。

示例话术：

> 本次用例和 BUG 已保存，但截图位于仓库外，目前尚未纳入已确认的备份范围。我会在交付索引中保留这个缺口，不能把它写成已完整备份。

> 这项需求已结束，可以移出默认活跃列表。原始材料、用例和证据仍然保留，后续按需求编号或业务名称可以找回。

只提示实际发现的问题和需要采取的动作，不每次重复长清单；只记录真实检查范围和时间，不把历史检查说成持续正常。

## 贯穿后续规划

| 阶段 | 必须纳入的长期使用设计 |
| --- | --- |
| 基础模型 | 稳定身份、历史版本、可恢复状态、索引与原文关系、保全范围 |
| 用户引导 | 找回旧任务、查阅历史规则、归档与重新开启、明确最近恢复点 |
| 各测试环节 | 材料和结论有来源，正式产物可追溯，证据完整，临时产物保留边界明确 |
| 工具与复用 | 外部引用失效处理、授权导出、格式与版本兼容、能力废弃后的替代路径 |
| Skill 实现 | 冲突检查、安全保存、按需与增量读取、可重建索引、迁移及回退 |
| 验证 | 中断、误删、附件丢失、引用变化、索引损坏、旧版本升级及规模增长演练 |
| 平台试用 | 换宿主或升级安装后，私有配置、产物路径和历史记录仍可接入 |
| 发布迭代 | 用户资料与安装包分离，说明支持的数据版本、升级方式及已知恢复限制 |

## 验收示例与待定内容

未来至少用以下演练核对方案：在独立目录从备份恢复一项旧需求及附件，重建损坏索引，模拟保存中断，恢复误删文件，升级旧状态格式，检查共享规则变更前后的依据，以及用虚构的增长数据量测量检索耗时与上下文用量。

恢复演练先在副本或隔离的测试目录进行；不覆盖用户当前唯一资料，不重放历史业务写操作。

待讨论：必须长期保存的材料清单、临时数据保留策略、归档条件、备份目标与频率、可接受恢复点、恢复演练方式及触发时机。确认这些原则后再设计具体文件与实现，不能仅凭本文件存在声称已保证不丢失。
