# 首次使用与接入项目

更新时间：2026-10-31。状态：第 2 步细化草案。基础版 0.1.0 已有简版接入说明；以下详细引导等待确认与体验验证，尚未写回实际 Skill。

## 本环节的目标

让用户知道现在可以从哪里开始，并使 Agent 找到本次任务需要的资料。用户无需先理解目录、MCP 或状态文件，也无需一次性配置整条测试流程。

完成本环节后，应能说清楚：在哪个 Agent 工作空间、属于哪个被测项目、处理哪项任务、这次做到哪里、依据哪些资料、下一步是什么。一个工作空间可能包含多个被测项目，详见 [归属与隔离设计](project-scope.md)。缺少的信息说明影响，不用猜测填满表单。

## 第 2 步如何推进

按推进计划的 2.1—2.6，依次讨论首次进入、渐进配置、过程引导、继续与切换、异常阻塞、体验走读与实际 Skill 更新。本轮只讨论 2.1。

每组示例明确：用户说了什么、Agent 已掌握什么、展示给用户什么、随后实际做什么、哪些需要保存。用户已知的信息不重复收集；内部标识、目录名、字段和 JSON 参数由 Agent 按约定处理。

## 2.1 首次进入与意图判断（本轮提议）

前提是用户已明确使用本 Skill 或当前请求属于其能力范围。这里设计激活后的体验，不假设已经验证任何宿主的自动触发机制。

### 先读已有信息，再判断是否需要补问

先核对用户本次请求、当前项目入口、相关项目或需求索引；按需读取明确关联资料，不遍历所有历史文件。

已有本地状态时通过 list/resume 定位。没有 workspace.json 时还应检查现有 README、项目规则、用例和用户指定材料，不能直接认定这是空项目。旧项目的正式资料先继续使用，不为统一结构自动初始化另一份权威状态或搬迁资料。

用户明确当前目标时直接进入对应工作。只有目标或项目归属的缺失会改变下一步动作时才补问，避免每次都要求选择“新项目／已有项目／继续任务”。

### 示例 A：首次使用，但还没说具体任务

用户：

> 我第一次用这个 Skill，想让你帮我做测试。

若读取当前目录后没有找到可直接关联的任务，建议回复：

> 我们先从你手上的任务开始。你现在要测哪个系统？如果已经有需求说明、原型或现成用例，直接给我就可以。

下一步根据回答选择分析、用例工作或执行准备；不把“做测试”自动理解为已授权在某个环境提交业务数据。

如果用户补充“暂时没有需求，只想先准备项目”，则进入项目接入，只补必要背景；运行目录与资料写入依用户实际授权推进，不提前索取登录密码或要求全部 MCP 就绪。

### 示例 B：用户已经给出明确任务

用户：

> 这是订单系统 71652 的需求说明，先帮我分析。

建议回复：

> 我先读取需求说明和这个项目已有的业务规则，梳理变更范围、涉及角色以及影响测试的疑问。

随后实际读取材料并开展已授权分析。材料足够时不重复询问所属项目或要求重新选择阶段；发现关键歧义后集中补问，不将尚未读取的资料描述为已经核对。

### 示例 C：用户直接继续已有需求

用户：

> 继续订单系统的 71652。

先读取该需求最近的有效记录。假设实际记录显示查看场景已完成、审批场景未执行，可以回复：

> 我找到了上次的进度：查看场景已经完成，审批场景还未执行。我会先核对当前用例和环境是否仍适用，再接着处理审批场景。

若此前只授权编写用例，则继续编写范围；没有执行授权时不能因“继续”自动开始页面操作。存在同号需求、过期依据或未知写操作时，再针对实际差异补问或回查。

### 本子项的完成依据

- 已有任务可以直接接入，未明确目标的用户能用自然语言提供最少信息。
- 开场通常用一小段说明当前工作，必要时补一个关键问题；不固定问卷，也不限制用户自由描述。
- 内部字段和配置检查不成为用户必须学习的前置知识。
- 不重复询问已知信息，不凭未读资料编造进度，不将讨论或分析扩大为业务执行。
- 对旧项目保留现有来源，对历史任务按需定位，符合长期使用与信息保全约定。

这些是待讨论方案，尚未完成真实新用户体验验证。

## 从用户当前任务选择入口

| 用户情况 | Agent 的建议行为 |
| --- | --- |
| 已给需求材料，要求先分析 | 读取材料和相关已有规则，直接开始分析；仅补关键缺失信息 |
| 空目录中说“帮我搭一个测试项目” | 了解系统及当前目标，逐步建立最小项目资料 |
| 已有项目首次使用 Skill | 先读项目入口及其引用的共享规则，定位正式产物和项目差异，保留现有目录与约定 |
| 新会话说“继续需求 12345” | 结合本会话任务和项目索引定位；不同项目存在同号需求且无法判断时，只询问所属项目，然后读取对应状态与交接 |
| 同一工作空间已有多个被测项目 | 使用已明确的项目绑定；不以另一个会话最后操作的项目作为本会话默认目标 |
| 只有一句“我想用这个 Skill” | 简短介绍能做什么，询问现在是开始新需求，还是接着已有任务做 |
| 用户直接指定用例执行或 BUG 操作 | 从指定任务接入，核对必要材料和权限；不要求重做前面所有环节 |

这些是 Agent 的内部判断分支，不要求用户每次填写选项或选择“运行模式”。已能从请求和项目资料判断时直接使用。

## 首次接入的最小信息

优先从当前目录、用户请求和已有资料确定：

1. 被测项目和相关系统身份：用稳定项目标识区分同名项目、同号需求；同一项目的客户端和管理端可以属于同一需求。
2. 本次目标：例如只分析、编写用例、执行一组场景、提交指定 BUG。
3. 当前可用材料：需求说明、原型、用例、业务知识或执行记录。

正式编号缺失不应阻止讨论；需要保存且存在重名风险时，采用明确的临时标识并保留后续映射。版本、作者简称、发版日期在命名和交付需要时补齐，不伪造值。

环境和账号在页面取证或测试执行前核对；缺陷平台字段在准备提交 BUG 时核对；知识库目标在需要检索或写入时核对。前一阶段不收集尚无用途的凭据或要求安装无关工具。

已有共享规范、模板或服务配置时先按适用范围复用，只收集本项目缺失的差异。引用方式与冲突处理见 [共享内容与项目差异](shared-resources.md)。共享内容的存在不表示可以直接执行其中所有操作。

## 推荐的对话方式

以下是话术示例，用来讨论体验；每次应根据事实自然表达。

用户已有需求说明：

> 我先帮你梳理这次改了哪些规则、涉及哪些角色，再把影响测试的疑问集中列出来。你提供的材料我会先读，缺少的关键内容再补问。

用户只有开始使用的意图：

> 我可以陪你从理解需求做到验证 BUG 修复。你现在是有一个新需求要开始，还是想接着已有的用例或测试记录继续？

接入已有项目，且已实际读取相关资料后：

> 我找到了项目约定和现有用例位置，会沿用它们。本次先处理你指定的需求分析，页面取证需要的环境信息到那一步再核对。

接入另一个被测项目，且共享范围已经确认后：

> 这个项目沿用团队的用例结构和 BUG 模板。我会复用这些约定，再补齐它自己的环境、业务规则和负责人信息。

新会话接续，且已核对最新记录后：

> 上次已完成新增和编辑场景，删除场景还未执行。已有失败场景和 BUG 的关联也已找到，本次从删除场景继续。

不同被测项目存在同号需求，且本次请求没有提供归属：

> 这里有订单平台和采购平台两项编号为 12345 的需求。你这次要继续哪一个？

归属已经明确时直接在进度说明中带上项目名称，不重复让用户选择。用户切换项目时，更新当前会话任务的绑定，保留其他会话原有任务。

工具当前不可用：

> 当前会话还不能编辑思维导图。我们可以先把业务场景讨论清楚；正式写入导图时，需要接通对应工具。我会保留未写入的状态。

不要在工具缺失时擅自改用另一种正式交付格式。说明可继续的独立工作，对依赖该工具的动作明确保留。

## 已有资料和冲突如何处理

- 先读项目入口和明确相关资料，按引用读取当前阶段需要的共享条目；不一次性读取所有历史需求或整个共享库。
- 已确认的信息不重复询问；状态缺少来源或明显过期时核对对应产物。
- 本次明确指令限定工作范围。项目规则、需求材料与实际观察冲突时说明差异，不静默覆盖。
- 当前页面行为不能直接替代需求规则。先判断是用例步骤过时，还是可能存在缺陷。
- “继续”不等于重新执行全部用例，也不等于自动提交所有本地 BUG。
- 结果不明的业务写操作先回查，不直接重发。无法确认时保留阻塞与所需证据。

## 目录建立与会话恢复

新项目先保存必要的入口和已确认信息。基础版已有 JSON v1 存储，本阶段设计什么时候使用这些能力；本轮不为真实项目生成运行配置。

已有项目保留既有产物位置，对外部正式用例、BUG 文件记录来源。基础版支持明确登记快照，尚未提供完整旧目录自动映射或迁移；引导时需如实说明可用范围。

多会话恢复至少需要工作空间与被测项目身份、需求身份、当前范围、产物及版本、未完成项、当前操作者和下一步。会话链接作为辅助入口，不作为唯一上下文来源。没有会话管理工具时，生成供用户带入新会话的简短开场。

恢复任务时核对本任务曾采用的共享版本；发现更新时说明受影响的规则或产物，按本次任务处理，不自动重写全部历史用例或重新执行测试。

首次进入任务只需给出简短开场说明“已知信息／本次工作／需要补充的关键项”。已获授权且无实质歧义时继续，不设置重复确认关卡。

## 本环节的完成依据与待讨论项

完成依据为提议：Agent 已能定位项目和任务、找到或明确缺失的材料、说明本次工作范围及下一步；不会因无关依赖未配置而阻塞当前工作。

当前优先讨论 2.1 的三种开场是否清楚自然，以及“先读已有信息，只补问影响下一步的内容”是否能帮助用户开始。确认后进入 2.2，细化新旧项目接入与信息收集时机。

以上话术和行为尚未通过独立使用验证。后续至少用“空目录首次使用”“已有项目直接分析”“新会话接续执行”“缺少工具”“多项目同号需求”“两个会话各自切换与续接”场景检查引导效果，再进入实现验收。
