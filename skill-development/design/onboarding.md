# 首次使用与接入项目

更新时间：2026-10-31。状态：第一版提议，等待讨论；不是已实现的 Skill 指令。

## 本环节的目标

让用户知道现在可以从哪里开始，并使 Agent 找到本次任务需要的资料。用户无需先理解目录、MCP 或状态文件，也无需一次性配置整条测试流程。

完成本环节后，应能说清楚：在哪个 Agent 工作空间、属于哪个被测项目、处理哪项任务、这次做到哪里、依据哪些资料、下一步是什么。一个工作空间可能包含多个被测项目，详见 [归属与隔离设计](project-scope.md)。缺少的信息说明影响，不用猜测填满表单。

## 从用户当前任务选择入口

| 用户情况 | Agent 的建议行为 |
| --- | --- |
| 已给需求材料，要求先分析 | 读取材料和相关已有规则，直接开始分析；仅补关键缺失信息 |
| 空目录中说“帮我搭一个测试项目” | 了解系统及当前目标，逐步建立最小项目资料 |
| 已有项目首次使用 Skill | 先读项目入口和规则，定位正式产物，保留现有目录与约定 |
| 新会话说“继续需求 12345” | 结合本会话任务和项目索引定位；不同项目存在同号需求且无法判断时，只询问所属项目，然后读取对应状态与交接 |
| 同一工作空间已有多个被测项目 | 使用已明确的项目绑定；不以另一个会话最后操作的项目作为本会话默认目标 |
| 只有一句“我想用这个 Skill” | 简短介绍能做什么，询问现在是开始新需求，还是接着已有任务做 |
| 用户直接指定用例执行或 BUG 操作 | 从指定任务接入，核对必要材料和权限；不要求重做前面所有环节 |

这些是 Agent 的内部判断分支，不要求用户每次填写选项或选择“运行模式”。已能从请求和项目资料判断时直接使用。

## 首次接入的最小信息

优先从当前目录、用户请求和已有资料确定：

1. 被测项目和相关系统身份：用稳定项目标识区分同名项目、同号需求；同一项目的客户端和管理端可以属于同一需求。
2. 本次目标：例如只分析、编写用例、执行一组场景、提交指定 BUG。
3. 当前可用材料：需求说明、原型、用例、业务知识或执行记录。

正式编号缺失不应阻止讨论；需要保存且存在重名风险时，采用明确的临时标识并保留后续映射。版本、作者简称、发版日期在命名和交付需要时补齐，不伪造值。

环境和账号在页面取证或测试执行前核对；缺陷平台字段在准备提交 BUG 时核对；知识库目标在需要检索或写入时核对。前一阶段不收集尚无用途的凭据或要求安装无关工具。

## 推荐的对话方式

以下是话术示例，用来讨论体验；每次应根据事实自然表达。

用户已有需求说明：

> 我先帮你梳理这次改了哪些规则、涉及哪些角色，再把影响测试的疑问集中列出来。你提供的材料我会先读，缺少的关键内容再补问。

用户只有开始使用的意图：

> 我可以陪你从理解需求做到验证 BUG 修复。你现在是有一个新需求要开始，还是想接着已有的用例或测试记录继续？

接入已有项目，且已实际读取相关资料后：

> 我找到了项目约定和现有用例位置，会沿用它们。本次先处理你指定的需求分析，页面取证需要的环境信息到那一步再核对。

新会话接续，且已核对最新记录后：

> 上次已完成新增和编辑场景，删除场景还未执行。已有失败场景和 BUG 的关联也已找到，本次从删除场景继续。

不同被测项目存在同号需求，且本次请求没有提供归属：

> 这里有订单平台和采购平台两项编号为 12345 的需求。你这次要继续哪一个？

归属已经明确时直接在进度说明中带上项目名称，不重复让用户选择。用户切换项目时，更新当前会话任务的绑定，保留其他会话原有任务。

工具当前不可用：

> 当前会话还不能编辑思维导图。我们可以先把业务场景讨论清楚；正式写入导图时，需要接通对应工具。我会保留未写入的状态。

不要在工具缺失时擅自改用另一种正式交付格式。说明可继续的独立工作，对依赖该工具的动作明确保留。

## 已有资料和冲突如何处理

- 先读项目入口和明确相关资料，按引用展开；不一次性读取所有历史需求。
- 已确认的信息不重复询问；状态缺少来源或明显过期时核对对应产物。
- 本次明确指令限定工作范围。项目规则、需求材料与实际观察冲突时说明差异，不静默覆盖。
- 当前页面行为不能直接替代需求规则。先判断是用例步骤过时，还是可能存在缺陷。
- “继续”不等于重新执行全部用例，也不等于自动提交所有本地 BUG。
- 结果不明的业务写操作先回查，不直接重发。无法确认时保留阻塞与所需证据。

## 目录建立与会话恢复

新项目先保存必要的入口和已确认信息。实际目录逐步增加；具体配置格式尚未确认，不在本设计阶段生成运行配置。

已有项目采用位置映射，不搬动或覆盖既有产物。对外部正式用例、BUG 文件记录引用；后续实现应检查引用是否仍有效。

多会话恢复至少需要工作空间与被测项目身份、需求身份、当前范围、产物及版本、未完成项、当前操作者和下一步。会话链接作为辅助入口，不作为唯一上下文来源。没有会话管理工具时，生成供用户带入新会话的简短开场。

首次进入任务只需给出简短开场说明“已知信息／本次工作／需要补充的关键项”。已获授权且无实质歧义时继续，不设置重复确认关卡。

## 本环节的完成依据与待讨论项

完成依据为提议：Agent 已能定位项目和任务、找到或明确缺失的材料、说明本次工作范围及下一步；不会因无关依赖未配置而阻塞当前工作。

下一轮优先讨论：

1. 只有使用意图、没有材料时，上述开场是否足够自然，能否帮助新用户开始。
2. 新项目的首次引导是否采用“先了解当前任务，随需要补项目配置”的方式。
3. 先确定多项目归属和任务状态模型，再设计具体配置字段及多会话交接机制。

以上话术和行为尚未通过独立使用验证。后续至少用“空目录首次使用”“已有项目直接分析”“新会话接续执行”“缺少工具”“多项目同号需求”“两个会话各自切换与续接”场景检查引导效果，再进入实现验收。
