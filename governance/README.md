# 测试流程治理

## 目标与分工

用户首次采用这种测试协作方式，希望通过实际使用持续改进，并使接手人能够沿用最新、经过验证的做法。

- **项目治理会话**：本仓库的协调与审计入口，负责测试方式、遗漏、框架设计和交接质量，不接受具体需求任务。可按用户要求读取需求文件、相关会话和授权项目知识，依据实际证据提出改进。
- **需求会话**：一个会话负责一个需求，维护本期材料、分析、用例、执行与知识同步结果，并在阶段结束时提醒复盘。
- **仓库文档**：保存现行规则、改进状态和证据。接手人不需要继承原会话记忆。

用户后续明确要求时，治理会话负责创建需求会话并准备开场。本次不创建需求会话。

## 提醒与审计触发点

| 时机 | 提醒或检查的重点 |
| --- | --- |
| 需求分析阶段结束 | 关键规则是否有依据；澄清是否减少歧义；是否有重复收集材料或信息丢失 |
| 用例评审完成 | 业务风险是否被覆盖；用例是否可执行、可分别判定；层级和细节是否方便实际使用 |
| 测试收尾（含阻塞暂停） | 结果是否有证据；遗漏和返工因何发生；知识同步和交接记录是否完整 |
| 实际发现影响结果的流程问题 | 当场指出具体问题及影响，不等周期结束 |
| 用户要求项目审计 | 读取指定需求、产物和必要的会话状态，说明已审计范围与未查看部分 |

每次复盘优先回答三点：什么做法有效，哪里造成遗漏或返工，下一次尝试改什么。短任务不必填写长报告；已有证据可直接引用，不重复抄录。

用户于 2026-09-20 选择在需求分析、用例评审和测试收尾时提醒复盘，不设置定时审计。阶段提醒由正在执行任务的需求会话依据 AGENTS.md 发出。治理会话不会因为其他会话有更新就自动运行；当前未创建定时自动化。

## 改进如何进入现行规范

1. 需求会话将实际发现及证据放入本期 README 的“流程复盘”，区分业务缺陷与流程问题。
2. 治理会话将跨需求或影响交接的发现汇总到 [改进记录](improvements.md)，说明问题、调整、验证方法和状态。
3. 选择必要的少量调整试行；观察是否减少遗漏、重复沟通或返工，是否增加不必要的维护负担。没有实际统计时不编造收益数字。
4. 验证有效后，更新 AGENTS.md、相关 context 文档或模板，并记录适用范围；效果不佳时撤回或修订，同时更新所有受影响的引用。

改进状态采用：待验证、试行中、已采纳、已撤回。待验证建议放在改进记录中，不直接成为所有需求的硬性要求。初始基线为试行中，不能因为文档已创建就声称流程有效。

更新通用规范属于治理会话的职责；当前用户已授权维护和优化这一框架。涉及新增服务、定时任务、外部写入或改变测试范围时，仍需遵循该行为的既有授权，不将流程改进视为无限授权。

## 审计结论与交接

审计说明查看了哪些需求、材料版本和执行批次。发现要给出具体证据、影响和下一步；未执行不能写成通过，工具可用不能写成业务测试已验收，未看到资料不能断言资料不存在。

接手时检查现行规则是否一致、需求是否能从入口继续、工具和账号获取方式是否明确、历史有效做法是否已进入规范。凭据仍由本机或适当的凭据渠道提供。
