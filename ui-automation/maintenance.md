# UI目录的跨会话维护约定

2026-10-21历史基线为1个平台、4项0.1.0能力。2026-10-28新增查询查看组合能力及[统一只读入口](runtime/README.md)，当前5项能力，其中2项接入新入口；已有详情函数仅增加调用元数据至0.1.1，源码未改。新入口已在授权的QA只读范围实测，尚不是完整执行器、写操作调度器或定时测试服务。

## 每个会话开始先查，再复用

1. 读 [目录入口](README.md)，运行 `node ui-automation/tools/catalog.mjs list --platform <平台ID>`，读取匹配项的 `get <能力ID>` 和必要的 `resolve <能力ID>`。这些命令只解析本地契约，不执行页面。
2. 核对当前能力版本、适配器、平台／端、支持环境、输入输出、前置、效果和limits，再读验证范围及证据。准备表单、只读回读、提交审批等效果不相同，不能按相似标题盲选。
3. 调用前实际确认环境、页面、身份和本次权限／数据范围；脚本中还有QA固定origin和已核对路径，不能改URL就当作支持UAT。
4. 需求README或用例公共流程记录使用的能力ID、版本、用途／输入输出及证据位置。当前版本不匹配或前置不满足时停止该片段，先查证，不自动取“最新”或使用旧副本。

已知且已接入的只读能力可以直接通过统一入口校验并执行，无需每次向模型展开完整源码和resolve输出。入口会加载契约、核对依赖与只读效果，记录源码/契约摘要；文件改变后拒绝沿用运行器旧缓存。默认summary只提供结论和证据入口，完整MCP调用保留在本机。首次理解新能力、排障或版本变化时再展开必要材料，核心协作规则及真实前置条件仍须核对。

## 谁维护什么

| 内容 | 维护方与位置 |
| --- | --- |
| 本期业务规则、用例、准备数据和实际执行证据 | 需求会话在 `requirements/<编号>/` 维护 |
| 经采样的可重复片段与契约 | 发现或修复的需求会话在对应平台／端／模块目录维护，提交前检查影响 |
| 目录分类、通用约定、跨需求冲突与交接质量 | 治理会话维护，结合具体证据调整 |
| `catalog.json` | 由工具生成，禁止手工改索引冒充实现已更新 |

同目录无独占锁。编辑既有共用能力前先检查Git状态、明确本轮负责的具体路径，避免多个会话同时编辑同一能力／platform.json／catalog.json；存在其他会话修改时先协调，不能覆盖、代为提交或创建worktree。契约变更在本需求README记录修改者所属任务、版本、原因和证据，使接手人能定位维护上下文。

需要通知其他依赖会话时，由用户直接授权或可核验的用户指令决定；文件关联不等于自动获得发消息权限。未获消息授权时记录受影响需求及待通知事项。不得声称当前有跨会话自动监听。

## 新片段如何进入目录

只有操作实证、尚无通用脚本时，可先将说明放在对应平台目录并由入口README链接，明确“资料、未登记可执行能力”；不要为了让catalog可检索而伪造入口或契约。示例为 [禅道提单交接](platforms/zentao/shared/bugs/submission-handoff.md)。有完整实现、恢复策略和证据后再登记platform.json／capability.json，当前资料型目录不表示工具已安装。

- 只沉淀真实页面中已识别的稳定片段；不为每条用例或需求复制一套脚本，不给陌生路径挂“已验证”。共享目录仅在行为与输入输出确实跨平台一致时使用。
- 采用现有 `platforms/<平台ID>/<端ID>/<模块>/<能力名>/`，包括 `run.js` 与 `capability.json`。平台环境登记在 `platform.json`，不按QA/UAT或需求编号复制实现。
- 沿现有契约填写稳定ID、版本、入口/runtime/adapter、输入输出、前置、effects、limits、环境、依赖及verification。在前置、输出或limits中说明权限、人工介入、配置阻塞、异步等待、部分完成和写结果未知如何处理，不发明当前工具不支持的新状态值。
- 参数化真实业务ID、账号显示名、标识和文本，不嵌入某次运行的单号、固定pageId、快照uid或凭据。长期页面定位与业务数据分别处理。
- 只读片段也可能改变导航／抽屉状态，需说明；写入片段须有目标唯一性及身份检查、只发起一次和结果回读策略。反馈不明返回待核对，调用方先查状态，不能重放提交探测结果。
- 仅准备不提交、反馈需另行回读等局限必须保留。不要为了统一返回格式掩盖已完成程度。

## 验证分层与状态

| 证据层次 | 能证明什么 | 不能推出什么 |
| --- | --- | --- |
| 已读说明或来源代码 | 了解实现与依赖 | 目标环境已可运行 |
| 本地语法／catalog检查 | 入口、契约、版本和引用可解析 | 登录、定位或业务通过 |
| 指定环境真实运行 | 该版本在特定角色、数据和路径下有证据 | 其他角色、审批配置、环境或全需求通过 |
| 新环境／角色补采 | 新增明确的验证范围 | 未执行的组合也自动验证 |

现有 `verification.status` 仅允许 `not-verified`、`verified`、`stale`、`blocked`。`verified`须同时读date、environment、scope、evidence，不能当全域通行证。运行时的 `blocked`、`reconcile_required` 等动作输出与契约验证状态是不同概念。

每项目前只有一份verification对象、一个现行实现版本；现有索引没有多环境验证矩阵或多版本执行机制。新增环境的证据先在需求runs与契约scope/limits说明清楚，不无依据地将支持环境等同实测环境；需要扩展数据结构时另由治理依据实际需求评估，不在本轮虚构已实现的能力。

## 页面漂移、修复和版本

1. 发现可见名称、布局、路由、权限／身份、请求触发、状态或异步行为与既有片段不符，记录实际差异及受影响ID。定位变化或来源依赖变化导致旧证据不再充分时，将契约标为 `stale`；纯业务权限／配置缺失可记 `blocked`，不要一律改定位器。
2. 保留最近有效证据和失效原因，在需求记录中链接；不删除旧证据、自动改为通过或为绕过阻塞扩大业务权限。
3. 修实现同步契约版本，记录行为变化：补丁用于兼容修复，新增兼容输入／输出可增次版本，不兼容语义／前置／效果变更增主版本。版本号描述实现，不是V7.32这类业务版本。
4. 实质修改后的实现缺少新运行证据时用 `not-verified`（无法运行则保留具体阻塞），不能把旧实现的verified直接移给新代码。仅文档措辞变化不制造虚假运行记录。
5. 用 `rg`检索旧能力ID和精确版本在 `capability.json`、需求README和公共流程中的引用；修订受影响依赖或明确阻塞。稳定ID保持不变，不为绕过版本不符另复制实现。
6. 运行 `node ui-automation/tools/catalog.mjs build` 再 `check`；核对索引变更只含本次目标，避免生成文件混入其他会话半成品。工具不能替代对需求文档引用和业务语义的检查。
7. 在有授权的最小真实路径重验后记录版本、日期、环境、角色／数据约束、预期／实际及证据，再限定scope恢复verified。被测新业务功能的用例状态仍独立记录。

## 外部认证依赖

[认证交接](platforms/salescloud/shared/auth/login-handoff-review.md) 已记录外部仓库路径、当时HEAD和三份来源文件哈希。原交接文件未被源Git跟踪，单凭源HEAD不足以固定内容，使用前核对文件存在及哈希；缺文件或漂移先补来源／复核，不默认使用磁盘最新代码，也不执行登录来试探依赖是否兼容。

账号、平台端、环境及日期的实际验证范围，以 [平台认证交接](platforms/salescloud/shared/auth/login-handoff-review.md) 及其中指向的运行证据为唯一维护入口；本通用约定不重复固定“只验证三个管理端账号”或“客户端尚未验证”等动态结论。是否已登记可执行auth能力另查当前catalog与真实实现，不能仅凭资料状态推定已交付；某账号认证桥的证据不自动推广到其他账号、CRM/IAM、UAT、完整Worker／快照恢复或被测SSO流程。凭据通过既有本机机制处理，索引不保存认证材料。

以后正式接入应先明确外部包版本／哈希、安装取得方式、平台环境与账号路由、隔离会话、人工介入、恢复和只读身份核验，再实现并登记auth能力；不能只增加一份capability.json占位或复制会话注入片段就称完整交付。本轮仅评估并保留来源，不复制外部包。

**71417等被测目标本身为登录时，必须走真实被测认证与回跳，不得用协议登录或会话注入替代。** 认证公共准备只能用于不绕过该用例目标的辅助条件，且须在已有验证和授权范围内。

## 正式执行中的资源与验证边界

- 实际下载要核对浏览器动作后的文件落地、可打开及内容／摘要；网络响应或Blob另存为文件不是浏览器下载完成。上传暂存、选择、页面条目和最终业务保存是不同阶段，不能以中间回执替代后续结果。
- Chrome DevTools的网页对话框接口与上传接口不能冒充原生下载保存窗口控制。若工具能力与当前浏览器上下文受限，记录具体阻塞，不能反复触发同一保存框。用户已确认的设置不重复要求修改，普通会话／隔离会话对照的结果和授权按任务范围保留，不推广为全局切换许可。
- 同时运行的需求各自拥有明确的上下文、页签、账号引用和数据，不清理或接管其他任务的Cookie、未提交表单或专用普通标签。SSO测试需要退出／清会话时仅作用于自己的上下文；发现同账号互踢先记录证据并协调，不能相互反复登录。
- 仅在用户明确授权并行时才分片；按场景node_id互斥分配，注明继承基线和新执行，已完成不重复跑、不重复累计。原正式Mind与总入口指定唯一写入方，其余执行者仅写自己分片结果、证据和BUG前缀；汇总者核对后统一回写，不能同时改一张Mind或同一业务单。
- 新执行者只读分派场景、必要公共流程和证据入口；共享片段经验证后参数化复用，但测点所需的提交次数、文字长度、改文与否、角色或状态条件不能为提速放宽。
- 并行执行不等于并行Git暂存／提交。明确提交负责人和文件边界，不夹带其他需求修改。没有模型成本对照时，不宣称并行一定更省Token。

## 每次需求收尾

- 登记本次复用、增加或修订的能力ID和版本，是否有页面漂移、未验证项和依赖影响。
- 核对契约与实现一致、catalog最新、证据可追溯，且真实业务结果已由需求runs记录。
- 测试数据／输出／截图归需求或本机目录；共用实现不保存运行结果。检查凭据与临时材料，不以忽略规则代替脱敏。
- 旧 `scripts/browser-flows/` 只维护迁移入口，不维护第二份实现；不要在新需求目录重新拷贝共享脚本。
- 附件暂存工具只负责将已授权非敏感文件复制至工具支持目录、返回大小与哈希；UI选择、上传完成、业务保存和临时目录清理分别核对，清理只限本轮自己创建的目录。
- 核对本次文件、版本、索引和依赖后按项目授权提交push；不夹带其他会话的修改。
