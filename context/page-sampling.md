# 真实页面采样与正式用例编写

来源：71652在2026-10-21的实际页面采样、用例补全及用户要求；治理会话已核对来源任务中的直接用户原文。此方法供后续需求按授权复用，不表示所有页面、角色或环境均已验证。

## 顺序与完成依据

1. **先确认完整需求。** 读取原型全范围、已确认规则、可用知识库和当前实际Mind文档。按“需求点→独立场景→涉及页面”在本需求README建轻量覆盖对照。不从现有导图剩余内容反推需求范围；用户删除示例不等于取消对应业务需求。
2. **查共用能力再定向采样。** 从 [UI目录](../ui-automation/README.md) 检索、读取契约及证据，按本轮目标找到缺失页面、组件、独特分支和业务状态，避免重复探索已确认路线。
3. **用真实观察补足操作。** 在授权条件内使用Chrome DevTools MCP，采到足以定位关键动作、身份和结果的依据即可停止，不把采样扩大为整套用例执行。
4. **回到需求写正式用例。** 根据真实组件文字描述操作；未部署功能用已确认需求规定预期，未实查的控件或路径明确标记。正式结构遵循 [用例范式v1.2](test-cases.md)。
5. **检查覆盖与保存。** 每个已确认需求点有对应用例，每个关键操作有真实依据或待核对标记；分别核对不同平台、页面和角色的独特条件。保存回读及文档检查不代表业务验收。

## 采样前落实条件

明确平台／端、目标环境和实际部署版本（未知注明）、角色、隔离浏览器会话、指定项目／数据、允许的造数与写操作范围及附件来源。已有明确条件直接沿用；只对无法查证且影响动作或验收的缺项提问。

允许编写用例不自动等于允许业务写操作。用户授权页面采样后，在明确边界内连续推进，不每一步重复请求许可。缺地址、权限、配置或需人工验证码时说明具体阻塞，继续不依赖该条件的材料整理，不假装已采样。

## 怎样采集并复用操作

- 页面操作统一使用Chrome DevTools MCP，不使用Computer Use。先观察陌生路径，记录可见菜单、页签、自动弹窗、字段、选项、按钮、滚动、异步就绪条件、账号切换及最终回读。
- 已实际核对的连续动作可参数化后复用，在导航完成、身份确认、提交和保存回读等关键边界检查；不要求每点一次都截图再推理。陌生分支先观察，不猜后续控件。
- 通过页面操作而非直接调用业务写接口完成UI采样；页面触发的请求／响应可作辅助证据，不能用HTTP结果代替界面和业务保存核对。
- 新建使用本轮唯一标识，创建后按该标识查回真实主单／子单ID和时间，再用于后续操作；不拿历史单、列表第一行或旧编辑标签中的号码当作创建结果。
- 写操作仅发起一次；结果未知先查询同一记录的权威状态，再决定后续。超时、成功提示、附件已选中或HTTP 200都不足以独立证明业务完成。
- 已采到足够组件与独特状态就停止，不为增加证据数量继续无关审批、接单或改历史数据。结束记录新建数据和实际停留状态，按约定处理数据。

71652曾观察到旧内部标签恢复、非空输入追加、筛选条件残留、抽屉遮罩未退场、审批表单异步重绘以及接单人与后续审批人不同等现象。它们可作定位思路，但其他需求需按当前实际页面验证，不能自动视为相同行为。

## 操作依据如何进入用例

- 用可见组件名称说明平台、角色、区域、动作、具体输入及结果，让后续执行者根据文字在DOM定位；不要求将CSS、XPath或快照uid写入正式用例，也不因采用本方法立即建设完整执行器。
- 每个场景分别有准备／操作／预期，操作各自从1开始；预期引用本场景步骤号。跨角色在同一场景中传递真实标识，并核对当前身份。
- 公共登录、导航、造数或流转流程必须有真实定义、输入和输出。不能用“打开子单S”掩盖未定义的导航及权限条件；S须由实际回读绑定。
- 测试附件写明文件名、内容和执行时生成方式。官方模板未部署时，标注部署后从官方模板制作测试副本；不自造一个模板声称模板功能已验证。
- 长文字确实要达到被折叠的条件，错误数据与数值边界要有可判定结果。合法边界缺基础数据时标记待准备，不擅自修改产品基础资料。
- 查看页与审批页、两种业务类型或不同角色有独特行为时分别覆盖，不能只检查二者相等而忽略二者可能同时错误。
- 区分原型规则、新功能设计、既有UI观察、用户确认和推断。未部署的新功能可以编写已知预期，但所有未执行场景仍标未执行；缺部署、数据或权限列明条件。

## 被测登录与公共认证准备

登录本身是被测功能时，必须走真实待测入口、认证、回跳及必要会话处理，不能以协议登录、会话注入或恢复快照跳过该链路再宣称SSO通过。

无关辅助角色准备只有在已验证适配范围和授权内才可考虑复用认证实现。具体已验证的账号、端、环境、日期和证据统一读取 [平台认证交接](../ui-automation/platforms/salescloud/shared/auth/login-handoff-review.md) 的最新限定范围，本通用说明不另行维护固定账号名单或“某端尚未验证”清单。认证资料存在不等于已交付可执行auth能力，需另查当前索引和入口；某个商用QA账号的认证桥成功不能自动推广到其他账号、CRM/IAM、UAT、完整Worker恢复或被测SSO链路。维护边界见 [UI目录维护](../ui-automation/maintenance.md)。

## 证据、Mind和交接

- 页面发现按需放 `requirements/<编号>/page-discovery-<日期>.md`，实际采样／执行事实放 `runs/`；README保留覆盖对照、依据入口、阻塞、产物、下一步及简短复盘，不额外堆成套报告。
- 可复用实现及契约归 `ui-automation/`，运行数据和凭据不进入共用实现；需求通过能力ID和当时版本关联，不复制实现。维护方式见 [目录维护约定](../ui-automation/maintenance.md)。
- 正式Mind通过MCP读取当前内容和未保存变化，按明确windowKey编辑、保存和完整回读，保留用户修改、密级、等级及真实历史结果。不离线重写已打开文档，已保存ZIP仅用于只读核对。
- 核对完整范围、场景三分支、独立编号、预期引用、公共流程、数据交接、折叠和未执行状态。中文批量写入若出现替代字符，定位后通过小批Mind修复并回读；写入慢或结果未知先查operation状态，不盲重放。
- 按2026-10-27用户追加要求，每个BUG至少包含一张经过标注的真实截图，使用 `screenshot-annotator` 并查看输出，确认对齐、可读、不遮挡证据；保留原图、规格和 `.evidence.json`。标注完成、复现、验收、提单分别记录。普通无BUG的过程截图无需机械加标注。

## 正式执行中的质量与反馈（2026-10-27补充）

- **实际完成优先。** 工具成功、HTTP200、页面Blob或选中文件不代表业务闭环。上传需等待文件条目和最终保存回读，避免上传中导航丢弃未提交表单；脚本操作失误记录为执行问题，不假报业务BUG或通过。
- **下载与上传分开。** 下载通过需真实浏览器动作完成、文件实际落地、可打开且内容符合预期；网络响应另存为文件只能证明响应内容，不代替下载成功。原生Save As可能不在页面快照内，handle_dialog不处理系统窗口，upload_file是上传选择器。遇此限制先核实当前工具与上下文，不反复触发窗口或要求用户改已经核对过的设置。浏览器模式切换和普通共享会话复用须有本任务适用授权，不能借用别的需求的一次对照许可。
- **不要把测试写法当作新增规则。** 必须核对原始要求和最新确认；用例自行要求的额外toast、序号算法或按钮样式不当然是验收标准。满足业务的操作差异据实修订用例，真正违反规则仍记录BUG。
- **澄清必须同步结果。** 最新规则在需求README主维护，关联正式Mind、运行结果、总体进度和BUG索引。重验具体受影响场景，误报移出有效BUG清单并归档原证据；不能只在聊天改口径，也不能盲目将全部失败改通过。
- **BUG直接给开发阅读。** 正文简单、自足，不使用内部C编号、节点ID或未定义变量代替说明。复现数据以文字或简洁表格展示；正文只含文字和内嵌标注图片，不放普通超链接、裸URL、输入文件／原图下载入口。完整原图、Excel、规格等保留本机assets，内部证据关联放runs。项目、计划、版本、指派按该需求用户原文，不能复制另一项目的固定字段。
- **失败数与BUG数分别统计。** 同根因影响多个场景可关联同一BUG，但要说明全部受影响页面与证据；不同触发条件／期望不能仅因属于同模块就合并。每条失败都要能追溯其BUG或未定原因，既不凑BUG数也不漏独立问题。
- **留意用例外明显UI问题。** 无1:1原型时，可据可读性、操作影响和上下文一致性判断明显文字错误、提示串用、遮挡、严重截断、异常空白／弹窗等。基于真实动作记录为“执行中探索发现”并附标注图，业务含义不明则保留现象及判断理由。此类发现不虚增原用例数，不扩成全站视觉审计。
- **总体进度可核算。** 活跃执行中每完成一组或约3—5分钟汇报总独立场景、通过、失败、真正阻塞、执行中、未开始、用户跳过／本期不适用；按场景node_id去重、总数对齐，公共流程另列。完成但待核验或待回写单列，不算环境阻塞。该频率是工作中的反馈约定，不是后台自动唤醒。

多执行者仅在用户明确授权时使用，划分互斥场景和单一Mind写入方、维护独立页面／数据；细则见 [UI目录维护](../ui-automation/maintenance.md)。这些方法来自71652的阶段实测与用户纠偏；不将其业务规则或未收尾的阶段数字推广到其他需求。

本地BUG提交到禅道属于另一个获授权的操作阶段。用户明确指定提交对象后，参考 [禅道提单交接](../ui-automation/platforms/zentao/shared/bugs/submission-handoff.md) 核对身份、动态字段、图片、单次创建及回读；API创建本身不证明所有字段和图片已保存。该提单方法不改变被测系统UI必须真实操作的验收边界，也不授权提交其他BUG。

图片交付需区分缓存可见、保存后服务器可读，以及有权访问该BUG的目标读者可见。71652的344562原图绕缓存请求为HTTP200但实际返回HTML“未找到文件”；用户手动重贴修复，新图绕缓存可读。后续344582通过正常UI表单及编辑器上传一次保存，在保存后及重新打开详情后均绕缓存读到与源图一致的PNG，用户随后确认同事也可见。该接收方证据来自用户确认，Agent未另用第二账号亲测；长期保存和原API图片路径已修复仍无证据。后续仍须执行这两次绕缓存核对，检查状态、MIME及非零图像内容／尺寸；图片未变化时才与原哈希比对，用户重新截图则更新来源。BUG创建事实保留，不重提或覆盖用户修复，不把具体丢失机制猜成已定位根因。
