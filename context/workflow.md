# 需求流程与交付约定

2026-09-20 对齐的试行流程。按实际使用持续优化，不代表已通过完整需求验证。

## 三类正式交付

1. **测试用例**：通过 asynctest-mind 编写和维护的 `.amind` 文件，明确版本、评审及执行状态。
2. **知识库内容**：本期确认的需求和业务知识，以及实际新增、更新的条目引用与同步结果。
3. **用户临时明确指定的产物**：例如测试数据、接口脚本、缺陷描述、汇报材料或测试报告；提出时加入本期交付清单，明确格式与完成状态。

分析笔记和必要执行证据按需保存在需求目录用于追溯，不默认生成额外的成套报告，也不要求用户重复整理。

## 从开始到结束

| 阶段 | 工作 | 阶段完成依据 |
| --- | --- | --- |
| 接收需求 | 读取需求说明、原型、版本和相关既有知识 | 明确本期目标、范围及材料版本 |
| 澄清规则 | 梳理流程、角色、数据规则、状态、异常及影响范围，集中讨论关键疑问 | 核心规则明确；剩余疑问有记录，明确受影响的用例 |
| 编写用例 | 先整理场景结构，再编写必要前置条件、操作和可核对的预期 | 形成可执行的思维导图初稿 |
| 评审与知识沉淀 | 检查遗漏、重复和可执行性，修订用例并整理知识正文 | 用例形成评审版；知识在用户授权及 MCP 确认流程后录入 |
| 按需执行测试 | 按指定范围由用户执行、Agent 协助或 Agent 执行 UI / 接口测试，保留证据 | 结果、缺陷与阻塞有记录；需求变化同步影响用例及知识 |
| 收尾复盘 | 核对最终交付版本、知识同步和未完成事项，简短复盘 | 接手人能定位当前规则、产物和下一步 |

流程不是所有阶段的自动执行授权。只要求分析和用例时，可以明确记录“测试未执行”后结束该工作阶段。后续进入其他阶段遵循用户指令，不为凑齐流程自动操作业务系统。

## 知识沉淀的内容与时机

- 需求编号、名称、来源版本、适用系统、业务目标及范围。
- 本次新增或调整的功能，以及相对原规则的变化。
- 已确认的业务流程、字段含义、计算口径、权限、状态和异常规则。
- 重要澄清结论及依据。
- 测试后值得复用的历史缺陷或限制，明确适用版本与验证状态。

用例描述“如何验证”，知识描述“业务如何规定”，两者关联，不机械复制整份用例。在需求澄清及用例评审后可以先沉淀确认规则，后续发生变化再更新对应条目，不必等全部测试结束。

待确认事项不得混为定论。实际系统表现与需求不一致时先记录差异或缺陷，不能直接将异常表现改写为正确规则。写入结果以 MCP 回执为准，保留引用并核对现行正文。

## 收尾交付索引

- 测试用例：文件、版本、评审 / 执行状态。
- 知识沉淀：新增或更新的条目及同步结果，尚未同步的内容。
- 指定产物：位置与完成情况；未要求则不额外生成。
- 未完成事项：阻塞、未测范围、待确认问题和下一步。

需求分析结束、用例评审完成、测试收尾时提醒简短复盘，记录证据支持的有效做法和实际问题，按 [流程治理](../governance/README.md) 汇总改进。
